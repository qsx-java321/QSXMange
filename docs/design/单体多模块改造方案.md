# QSXManager 单体多模块改造方案

> 状态：**已实施**（2026-09-18，分支 `refactor/multi-module`）
> 验收结果：6 个模块 `mvn -o -DskipTests compile` 全绿 → `mvn -o test` **138 例全绿**（改造当轮基线；此后已补齐角色/权限/菜单/日志用例，当前基线 **171 例**，见 `docs/test/项目测试报告.md`）→ fat jar 运行期冒烟通过
> 行为契约：**纯搬运，运行时行为零变更**（接口结构、错误码、Redis 键、审计链路均与改造前一致）
>
> 本文档保留**计划原文 + 3 轮审查记录**：正文说明「改造前 → 改造后」的设计与依据，附 B 记录 16 处审查修正（其中 1 处是实施阶段被编译器兜住的）。文中的文件链接已同步为改造后的模块路径。

## 一、目标与约束

### 1.1 目标

1. 把单模块 `com.qsx:qsx-manager` 拆为 **5 个 Maven 模块**，依赖方向严格单向、**无环**。
2. 认证鉴权内核（会话三键 + Lua 原子脚本 + 权限缓存）可被其他项目**单独复用**。
3. 新增业务模块只需「加一个 jar + 加权限码」，不触碰内核代码。

### 1.2 硬约束（评审红线，任何一条被破坏即视为失败）

| # | 不变式 | 为什么是红线 |
|:--|:--|:--|
| 1 | 全部 34 个 HTTP 路径、方法、请求/响应 JSON 结构不变 | 前端契约 |
| 2 | 26 个业务错误码（1001–1026）的数值与文案不变 | 前端按码分支 |
| 3 | Redis 键三前缀 `qsx:auth:at:` / `qsx:auth:rt:` / `qsx:auth:session:` 与 `qsx:auth:perm:` 不变 | 在线会话存续 |
| 4 | `resources/lua/*.lua` 三个脚本**一字不改** | 原子语义 |
| 5 | 23 个权限码常量值不变，控制器 `@PreAuthorize` 表达式不变 | 鉴权 |
| 6 | 控制器仍在 `com.qsx.web.controller` 包下 | `OperationLogAspect` 切点契约 |
| 7 | Mapper 仍在 `com.qsx.mapper` 包下 | `@Mapper` + `com.qsx` 扫描根 |
| 8 | 实体仍在 `com.qsx.domain.entity` 包下 | `mybatis-plus.type-aliases-package` |
| 9 | `application.yml` 全部配置键不变（含 `import.default-password`、`qsx.rbac-cache.*`、`qsx.auth.session.*`） | 配置契约 |
| 10 | 测试用例数与断言强度不变，`mvn -o test` **全绿** | 验收标准 |

> 注意第 6/7/8 条：本方案**不动业务模块（qsx-module-system）的包结构**，只动基础设施模块（common/security/framework）的包名。这是"零变更"与"边界清晰"的折中，也是切面与 MyBatis-Plus 能继续工作的前提。

## 二、模块清单

| 模块 | artifactId | 职责 | 编译期依赖 | 源文件数（现有 → 改造后） |
|:--|:--|:--|:--|:--|
| 通用契约 | `qsx-common` | `Result` / `ResultCode` / `BusinessException` + 跨模块端口接口 | lombok | 3 → 5 |
| 认证内核 | `qsx-security` | Spring Security 装配、令牌过滤器、会话三键 + Lua、权限缓存、`SecurityUser`、`SecurityUtils` + **端口定义** | `qsx-common` | 21 → 24 |
| 技术底座 | `qsx-framework` | MyBatis-Plus 配置、异步线程池、`PageResult`、全局异常处理、操作日志切面 | `qsx-security` | 5 → 5 |
| 系统业务 | `qsx-module-system` | 用户 / 角色 / 权限 / 菜单 / 日志 / Excel + **端口实现** + 全部实体与 Mapper | `qsx-framework` | 59 → 61 |
| 启动器 | `qsx-admin` | 启动类、`application.yml`、集成测试 | `qsx-module-system` | 1 + 17 测试 |

> 现有主源文件合计 **89** 个（`common 7 / security 13 / config 7 / domain 7 / mapper 6 / service 14 / web 33 / aspect 1 / 启动类 1`），改造后 **96** 个（新增 7 个：端口 3 个 + 端口契约 2 个 + 端口实现 2 个）。

**依赖链**：`qsx-common → qsx-security → qsx-framework → qsx-module-system → qsx-admin`（严格线性，无环）

**artifact 命名约定**：基础设施用 `qsx-<能力>`，业务模块统一用 `qsx-module-<域>`。以后新增业务即 `qsx-module-order`、`qsx-module-demo`。

### 为什么这样分而不是按 web/service/mapper/domain 横向分

现有代码是**逻辑分层**：`service` 层直接 import `web.dto`/`web.vo`（向上依赖），`security` 层直接 import `mapper`/`service`（向下穿透）。按包名横向切会立刻产生三个环。本方案改为**模块级纵切**：每个业务域自带 controller + service + mapper + entity + dto/vo 在同一个 jar 内，`service → web` 那条向上依赖就自然消失了（变成了模块内部依赖）。

## 四、解环设计

### 4.1 端口总表（4 个，编号与后文小节一致）

| 编号 | 端口 | 定义位置 | 现在的问题 | 实现位置 |
|:--|:--|:--|:--|:--|
| ① | `AuthUserAccount` + `AuthUserRepository` | `com.qsx.security.port` | `SecurityUser` 持有业务实体 `User`；`SecurityUserDetailsService` 直接注入 `UserMapper` | system（`UserMapper` 适配） |
| ② | `UserAuthorityRepository` | `com.qsx.security.port` | `PermissionCacheServiceImpl` 回源 SQL 直接走 `UserMapper` | system（`UserMapper` 适配） |
| ③④ | `AccessLogCommand` + `AccessLogRecorder` | `com.qsx.common.log` | 4 个审计补记点（2 个 handler + 切面 + 全局异常）都注入 `OperationLogService` | system（`OperationLogServiceImpl` 实现） |

> 全部采用「内核定义接口、业务模块提供实现」的依赖倒置。运行时由 Spring 注入，编译期 `security` 不反向依赖 `system`。
>
> 端口①之所以合并成一个编号：`AuthUserAccount` 是数据契约、`AuthUserRepository` 是取数接口，二者改的是同一件事（让 security 不再认识业务实体 `User`）。

### 4.2 端口 ① `AuthUserAccount` + `AuthUserRepository`

新增 `com.qsx.security.port.AuthUserAccount`（record，字段与 `User` 实体的认证相关字段一一对应）：

```java
public record AuthUserAccount(
        Long id, String email, String nickname, String password,
        Integer status, LocalDateTime createTime, LocalDateTime updateTime) {
    /** status: 0-正常，1-禁用 */
    public boolean enabled() { return status != null && status == 0; }
}
```

```java
public interface AuthUserRepository {
    Optional<AuthUserAccount> findByEmail(String email);   // 对应 UserMapper.selectOne(email)
    Optional<AuthUserAccount> findById(Long userId);       // 对应 UserMapper.selectById(userId)
}
```

system 侧适配器 `AuthUserRepositoryImpl`：注入 `UserMapper`，查询后转 `AuthUserAccount`，`@TableLogic` 行为完全保留。

### 4.3 端口 ② `UserAuthorityRepository`

```java
public interface UserAuthorityRepository {
    List<String> selectRoleCodes(Long userId);        // 对应 UserMapper.selectRoleCodes（过滤 r.status=0）
    List<String> selectPermissionCodes(Long userId);  // 对应 UserMapper.selectPermissionCodes
}
```

system 侧适配器直接委托 `UserMapper` 的同名方法，**SQL 与过滤条件原样透传**——特别是不许改动 `selectRoleCodes` 的 `r.status = 0` 条件（停用角色即时回收权限依赖它）。

`PermissionCacheServiceImpl` 改为注入该端口，其余逻辑（Redis 优先、未命中回填、空权限防穿透、fail-open 降级）**一行不改**。

### 4.4 端口 ③④ `AccessLogCommand` + `AccessLogRecorder`

新增 `com.qsx.common.log.AccessLogCommand`（record，字段与 `OperationLog` 实体的写入字段一一对应）：
`userId, username, method, url, httpStatus, success, errorMsg, costMs`

```java
public interface AccessLogRecorder {
    void record(AccessLogCommand command);
}
```

**改造点共 4 处**（全部是 `new OperationLog()` 的构造点，逐处已核实）：

| # | 位置 | 现注入 | 改注入 |
|:--|:--|:--|:--|
| 1 | `OperationLogAspect.initLog()`（framework） | `OperationLogService` | `AccessLogRecorder` |
| 2 | `GlobalExceptionHandler`（framework） | `OperationLogService` | `AccessLogRecorder` |
| 3 | `RestAuthenticationEntryPoint`（security） | `OperationLogService` | `AccessLogRecorder` |
| 4 | `RestAccessDeniedHandler`（security） | `OperationLogService` | `AccessLogRecorder` |

取当前用户、`Result.code==200` 成功判定、401 基础设施故障跳过落库（`AUTH_INFRA_ERROR_ATTR`）等**分支逻辑不动**。

> ⚠️ 但有一处必须改：这 4 个位置都用 `securityUser.getUser()` 取用户名与 ID（返回业务实体 `User`），改造后要换成 `account`（**详见 4.6，共 6 处**）。不要被上面"分支逻辑不动"误读成"整段照抄"。

#### ⚠️ 必须避开的陷阱：`@Async` 自调用失效

现状 [OperationLogServiceImpl.asyncSave()](file:///d:/Java_SE/Git/QSXManager/qsx-module-system/src/main/java/com/qsx/service/impl/OperationLogServiceImpl.java#L31-L41) 上的 `@Async("operationLogExecutor")` 之所以生效，是因为它由**外部 Bean**（切面/处理器）调用，走的是 Spring 代理。

**若把 `record()` 写成"内部调用 `this.asyncSave(...)`"，自调用不经过代理，`@Async` 会静默失效——日志落库退化为同步，主请求被数据库写入阻塞。** 这是本次改造最容易踩的坑，且不会有编译错误。

**采用方案**：让 `record()` 自身成为异步方法，直接落库，并删除已无调用方的 `asyncSave`：

```java
@Override
@Async("operationLogExecutor")
public void record(AccessLogCommand command) {
    try {
        operationLogMapper.insert(toEntity(command));   // toEntity 只做字段搬运
    } catch (Exception e) {
        log.error("操作日志落库失败: userId={}, url={}, cost={}ms",
                command.userId(), command.url(), command.costMs(), e);
    }
}
```

- `OperationLogServiceImpl implements OperationLogService, AccessLogRecorder`（同一个 Bean，`record` 由外部调用 → 代理生效）。
- 同步删除 `OperationLogService.asyncSave(OperationLog)` 与实现（唯一调用方是上表 4 处，全部已改用 `record`，已核实测试中无引用）。
- 异步线程池 Bean 名 `operationLogExecutor` 定义在 framework 的 `AsyncConfig`，跨模块按名字引用，运行时解析正常。

### 4.5 `SecurityUser` 去实体依赖

`SecurityUser` 的 `User user` 字段 → `AuthUserAccount account`：

| 现有实现 | 改后 |
|:--|:--|
| `getPassword() { return user.getPassword(); }` | `getPassword() { return account.password(); }` |
| `getUsername() { return user.getEmail(); }` | `getUsername() { return account.email(); }` |
| `isEnabled() { return user.getStatus() != null && user.getStatus() == 0; }` | `isEnabled() { return account.enabled(); }` |
| `getUser()` | `getAccount()` + 新增 `getId()` / `getEmail()` / `getNickname()` |

`getAuthorities()` 的 `ROLE_` 前缀逻辑、双参构造、`loadUserById` 必须同时填充 roles/permissions 的约定**全部保留**。

### 4.6 `SecurityUser.getUser()` 的调用点（已穷举 import 边 + 逐文件核实）

`getUser()` 返回业务实体 `User`，改造后返回 `AuthUserAccount`。**直接书写 `getUser()` 的位置共 6 处**：

| # | 位置 | 模块 | 改法 |
|:--|:--|:--|:--|
| 1 | `SecurityUtils.getCurrentUser()` L26 | security | 返回 `securityUser.getAccount()`；未登录抛 401 的行为不变 |
| 2 | [AuthServiceImpl.login() L91](file:///d:/Java_SE/Git/QSXManager/qsx-module-system/src/main/java/com/qsx/service/impl/AuthServiceImpl.java#L90-L91) | system | `((SecurityUser) authentication.getPrincipal()).getAccount()`；后续 L94/102/103/104 取 `id/email/nickname` 改 record 访问器 |
| 3 | `OperationLogAspect.initLog()` L111-112 | framework | `getAccount()` → 本处直接构造 `AccessLogCommand` |
| 4 | `GlobalExceptionHandler.recordAccessLog()` L85-86 | framework | 同上 |
| 5 | `RestAuthenticationEntryPoint.recordAccessLog()` L71-72 | security | 同上 |
| 6 | `RestAccessDeniedHandler.recordAccessLog()` L62-63 | security | 同上 |

**另有 3 处不直接写 `getUser()`、但依赖其返回类型 `User` 的间接调用点**（经 `SecurityUtils.getCurrentUser()` 拿到 `User`）：

| 位置 | 模块 | 改法 |
|:--|:--|:--|
| [AuthServiceImpl.me() L163](file:///d:/Java_SE/Git/QSXManager/qsx-module-system/src/main/java/com/qsx/service/impl/AuthServiceImpl.java#L161-L166) | system | 返回类型变 `AuthUserAccount` → `UserVO` 新增 `from(AuthUserAccount)` 重载；返回结构不变 |
| [AuthServiceImpl.changePassword() L169](file:///d:/Java_SE/Git/QSXManager/qsx-module-system/src/main/java/com/qsx/service/impl/AuthServiceImpl.java#L167-L187) | system | 改用 `account.password()` / `account.id()`；**改密后清会话 + ERROR 告警的语义、以及"必须在密码落库成功之后调用"的顺序约束一字不改** |
| `PermissionServiceImpl.getUserMenuTree()` L177 | system | `AuthUserAccount current = SecurityUtils.getCurrentUser();` → `current.id()` |

> **第 2 处（`login()`）与第 3~6 处是最容易漏的。** `login()` 用 `user.getId()` 签发会话（L94）、取 `email`/`nickname` 填 `LoginVO`（L102-104）；第 3~6 处是 4 个审计补记点，它们分散在 framework 与 security 两个模块，"只换 service 注入、忘换实体读取"会直接编译失败。
>
> 合计需要触碰的代码点：**6 处直接 + 3 处间接 = 9 处**。
>
> ⚠️ 第 3 行（`PermissionServiceImpl.getUserMenuTree()`）是**实施阶段才被编译器捕获的**：前两轮审查只 grep 了 `getUser()`，而这处走的是 `SecurityUtils.getCurrentUser()`。只 grep 直接调用会漏掉"经工具类间接取用户"的路径——**排查同类改造时，必须同时 grep `getCurrentUser` 与 `getUser()`**。

#### `AuthUserAccount` 字段必须覆盖全部调用点

由上表倒推，record 必须包含：`id`、`email`、`nickname`、`password`、`status`、`createTime`、`updateTime`（后两个供 `UserVO` 使用）。`enabled()` 提供 `status != null && status == 0` 谓词——**必须与 `UserServiceImpl` 的「非 0 即禁用」保持同一谓词**（现有注释明确要求两者一致）。

#### `loadUserByUsername` 的异常语义必须保留

现有实现查不到用户时抛 `UsernameNotFoundException("邮箱或密码错误")`（[L36-38](file:///d:/Java_SE/Git/QSXManager/qsx-security/src/main/java/com/qsx/security/service/SecurityUserDetailsService.java#L32-L42)）。改成端口返回 `Optional` 后，security 侧**仍要抛同一个异常、同一句文案**，否则 `BadCredentialsException` 的转换链会变，登录错误码 1002 会失配。

> 注意：`SecurityUser` 的 `getAuthorities()` 的 `ROLE_` 前缀、`loadUserById` 必须同时填充 roles/permissions 的约定（否则所有 `@PreAuthorize` 变 403）**全部保留**。单参构造 `SecurityUser(User)` 经核实**无调用方**（仅 `SecurityUserDetailsService` 用双参构造），可连同改造或直接删除。

## 七、包名与切点契约

| 契约 | 规则 |
|:--|:--|
| 组件扫描 | 启动类仍在 `com.qsx`，`@SpringBootApplication` 默认扫描 classpath 上全部模块的 `com.qsx.*` 子包，**不需要加 `scanBasePackages`** |

> 两个选择：
> - **保持现状（默认）**：零 import 改动，代价是包名与模块名不一致；
> - **改为 `com.qsx.system.constant`**：边界更清晰，代价是改 2 个测试文件的 import（`AdminProtectionTest`、`UserEdgeTest` 引用 `PermissionConstants`），以及 7 个 controller/service 的 import。改动纯机械、零行为影响。

| 风险 | 影响 | 缓解 |

| 搬迁漏改 import 导致编译失败 | 阻塞 | `mvn -o -DskipTests compile` 逐阶段验证；IDE 重构优先于手工改 |

### 复用性约束（写进文档，不是本次要解决的问题）

从上面的依赖边穷举结果看，**只依赖 `qsx-security`（而不引入 `qsx-module-system`）的消费者，必须自己提供 3 个 Bean**，否则容器启动即失败：

| 必须提供的 Bean | 定义在 | 用途 | 不提供时的报错时机 |
|:--|:--|:--|:--|
| `AuthUserRepository` | `qsx-security` | 认证时按 email / id 取用户行 | 启动期 `NoSuchBeanDefinitionException` |
| `UserAuthorityRepository` | `qsx-security` | 权限缓存未命中时回源角色码/权限码 | 启动期 `NoSuchBeanDefinitionException` |
| `AccessLogRecorder` | `qsx-common` | 审计落库（由 `security` 的 2 个 handler 与 `framework` 的切面/异常处理器注入） | 启动期 `NoSuchBeanDefinitionException` |

另有 2 项运行时前置条件（非 Bean）：**Redis 必须可用**（会话层 fail-closed，故障即全员 401）、**需提供 `qsx.auth.session.*` 与 `qsx.rbac-cache.*` 配置项**（`AuthSessionProperties` 有启动期 `@AssertTrue` 校验，缺失或纯数字会被拒）。

**处理方式**（本次取第一项，第二项不做）：

- **推荐**：在改造后的 `README` / 新模块模板中显式声明这份「复用清单」，并提供 3 个空实现/最简实现的样例代码；
- 或者：把 `security` / `framework` 侧的注入改为 `ObjectProvider<X>`，取不到就跳过对应能力。这会引入与现状不同的分支（当前总是有实现），属于「非纯搬运」改动，**本次不做**。
