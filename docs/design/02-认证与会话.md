# 02 · 认证与会话

> 本项目**最需要先读懂**的部分。所有「登录/登出/踢人/禁用/改密/刷新」的行为都由这里决定。

## 1. 没有 JWT，令牌是随机串

access token（AT）与 refresh token（RT）都是 **32 字节 SecureRandom 的 hex 编码（64 字符）**，
**无签名、无载荷、不可解析出任何用户信息**。

为什么放弃 JWT：

| 维度 | JWT（无状态） | 本项目（Redis 有状态随机串） |
| :--- | :--- | :--- |
| 吊销 | 只能等自然过期（或维护黑名单，等于又回到有状态） | **删 Redis 键即吊销**，登出/踢人/禁用/删除/改密即时生效 |
| 用户数据变更 | 改邮箱后载荷里的 email 失配 | 令牌里没有数据，改什么都不影响 |
| 依赖 | 无 | **硬依赖 Redis**（见 §7 fail 策略分级） |

代价是每次请求多一次 Redis 查询——换来的是「吊销即时生效」这条本项目最核心的保证。

## 2. 三键模型

| Key | Value | TTL | 职责 |
| :--- | :--- | :--- | :--- |
| `qsx:auth:at:{at}` | userId | 30m | AT 有效性；**删除即吊销** |
| `qsx:auth:rt:{rt}` | userId | 7d | RT → userId；轮换时删旧立新 |
| `qsx:auth:session:{userId}` | Hash`{accessToken, refreshToken, firstLoginTs}` | 7d 滑动 | 单端覆盖的索引、按用户清理的入口、30 天绝对上限的依据 |

为什么是三个键而不是一个：

- **AT 与 RT 分开**：AT 短（30m）、RT 长（7d），两者生命周期不同，分开才能各设 TTL。
- **索引键按 userId**：所有「按用户清理」的场景（踢人、禁用、删除、改密）只知道 userId，
  必须有一个以 userId 为键的入口去反查当前令牌，否则清理就要扫全表。
- **`firstLoginTs` 只在登录时写**：轮换不更新它，因此它天然就是「会话绝对上限」的起点。

前缀常量的**唯一来源**是 `AuthRedisKeys`，并由 Java 侧以 ARGV 传给 Lua（脚本内需要按
「只有进脚本后才知道」的令牌值反查并删除旧键，前缀不能在脚本里写死）。

## 3. 三条 Lua 脚本（改会话行为前先读脚本头部注释）

全部多键操作走 Lua，位置：`qsx-security/src/main/resources/lua/`——**脚本必须与使用方同模块**，
否则 `ClassPathResource` 加载失败。三条脚本都用 `DefaultRedisScript` 注册在 `AuthSessionLuaConfig`，
**必须用 `@Qualifier` 按 Bean 名注入**（同类型多 Bean，按类型注入会 `NoUniqueBeanDefinitionException`）。

### 3.1 `auth_session_issue.lua` —— 登录签发（含单端覆盖）

```
1. 参数校验（先于任何写操作：Lua 报错不回滚已执行的写）
2. 读旧 session 的 accessToken/refreshToken → DEL 旧 at / rt   ← 单端覆盖
3. 先 HSET session（写入新令牌 + firstLoginTs）并 EXPIRE
4. 再 SET 新的 at / rt 键
```

两条被反复踩过的约定：

- **读 Hash 字段必须 `HGET`，不能用 `HGETALL`**：RESP2 下后者返回 Lua 数组而非 map，
  `old.accessToken` 恒为 `nil` → 旧 AT 永远删不掉 →「即时踢下线」**静默失效**。
- **写入顺序固定为「先清旧 → 写 session → 写令牌键」**：中途失败时留下的是
  「会话指向一个不存在的令牌」（死令牌，安全），而不是「活着的、会话不知情的令牌」
  （无法吊销，危险）。

### 3.2 `auth_session_rotate.lua` —— 刷新轮换（五步判定）

```
1. rt → userId（查不到 → INVALID）
2. 双保险：session.refreshToken 必须与本次使用的 rt 完全一致（否则 INVALID）
3. firstLoginTs 容错：缺失/非法 → 直接作废整个会话（fail-safe）
4. 绝对上限：now - firstLoginTs > maxLifetime → 删除会话与令牌 → EXPIRED
5. 轮换：删旧 AT、删旧 RT，写新 AT/RT（firstLoginTs 保持不变）
```

- **第 2 步是本脚本的承重墙**：它同时拦掉「已被新登录覆盖的旧 rt」与「已被轮换掉的旧 rt」，
  也是「脚本中途失败后残留的旧 rt 键无害」的保证。
- **第 5 步必须删旧 AT**：只换 RT 不换 AT 就等于留一个 30 分钟的踢人漏洞。
- 返回 `'status|userId'` 单字符串而非 Lua 表：表在 Java 侧只能映射为原始 `List`（无法带元素泛型），
  统一成字符串可让三条脚本保持同一结果类型。

### 3.3 `auth_session_remove.lua` —— 统一清理

读 session 的 at/rt 字段 → 删两个令牌键 → 删 session 键。幂等（会话不存在同样返回 OK）。

## 4. 请求链路

```
Authorization: Bearer <at>
  → TokenAuthenticationFilter：Redis GET qsx:auth:at:{at} → userId
      ├─ 查不到 → 未认证（令牌从未签发 / 已过期 / 已被吊销 / 已被单端覆盖）
      └─ 查到 → SecurityUserDetailsService.loadUserById(userId)
                  ├─ 实时查库取用户行（@TableLogic 过滤已删用户）
                  ├─ isEnabled()：status != 0 即禁用 → 未认证
                  ├─ must_change_password=1 且请求不在 /auth/ 下
                  │     → 直接写「HTTP 200 + body 1037」并结束（不写 SecurityContext）
                  ├─ 权限码走 Redis 缓存（未命中回源并回填）
                  └─ 写入 SecurityContext
  → URL 级 authenticated() + 方法级 @PreAuthorize 双重校验
```

**每请求一次 Redis GET + 一次实时查库**，因此禁用、删除与「首次改密」的解除都即时生效（不必重启、不必等 TTL）。

> **为什么这道闸放在这里而不是别处**：用户行本来就每请求实时查库，标志因此天然即时、
> 零额外开销，**不需要动三条会话 Lua、也不需要缓存失效**。它与 `isEnabled()` 同源，
> 但**刻意不参与 `isEnabled()`**：那条路会被 `DaoAuthenticationProvider` 抛成
> `DisabledException` → 1003（账号禁用），而"必须先改密"的账号**恰恰需要能登录**——
> 不登录就没有会话，没有会话就改不了密码。


## 5. 刷新语义（前端契约）

```json
POST /auth/refresh   { "refreshToken": "..." }
```

- **严格轮换**：旧 RT 一经使用立即失效，其对应的旧 AT 也随之失效。重放旧 RT → `1019`。
- **必须单飞**：并发刷新时只有一个成功，其余返回 `1019`。
- **滑动 + 绝对上限**：每次轮换续期 7 天，但自首次登录起 30 天封顶，轮换不续命。
- **失败码统一**：除「未携带 refreshToken」返回 400 外，一切刷新失败（形态非法、未知、已轮换、
  超上限、Redis 故障）统一返回 `1019`——不向客户端泄露失败细节。
- **查库在轮换之前**：若先轮换再查库，一旦数据库抖动就会「旧令牌已销毁、新令牌没发出去」，
  等于白白烧掉用户的有效会话。这段顺序的原因写在 `AuthServiceImpl.refresh` 的注释里。

## 6. 吊销与会话清理：六入口统一收口

**统一入口是 `AuthSessionService.remove(userId)`**，调用点共六处：

| 入口 | 行为 | 失败策略 |
| :--- | :--- | :--- |
| 登出 `/auth/logout` | 清理自己的会话 | **降级为成功**（登出以用户意图为准，避免界面卡死），仅 WARN |
| 踢人 `POST /api/users/{id}/kick` | 清理目标会话（不改账号状态） | 抛出（fail-closed），由全局兜底 500 |
| 禁用 `PUT /api/users/{id}`（status≠0） | 清理目标会话 | 仅告警不阻断（每请求查库的 `isEnabled()` 是第二道防线） |
| 删除用户 `DELETE /api/users/{id}` | 清理目标会话 | 仅告警不阻断；**放在事务提交后**执行 |
| 改密 `POST /auth/change-password` | 清理自己的会话 | **ERROR 告警**不阻断——改密没有任何「每请求查库」的兜底网，此处失败即意味着止损没生效 |
| 忘记密码重置 `POST /auth/forgot-password` | 清理自己的会话 | 同改密（匿名通道，邮箱可达即凭据可改） |

> **新增任何涉及账号状态或凭据的用户生命周期变更，必须一并清理会话**，否则旧令牌仍然有效。

## 7. fail 策略分级（边界不可混淆）

| 链路 | 策略 | 原因 |
| :--- | :--- | :--- |
| 会话（AT 校验 / 签发 / 轮换 / 清理） | **fail-closed** | 令牌是随机串，Redis 之外无法确定身份；宁可拒绝认证也不错误放行 |
| 权限缓存 | **fail-open** | 降级实时查库，业务可用性优先（且此时会话链路已经拒绝了，不会真的放行） |

Redis 故障时的既定行为与降噪措施：

- 全部请求 401；`TokenAuthenticationFilter` 打 ERROR 留痕并给请求打标记。
- **该标记让 401 处理器跳过审计落库**——否则故障期 100% 请求都 401，逐条写库会把
  「Redis 局部故障」放大成「数据库写风暴」。

## 8. 设计约束

| 约束 | 说明 |
| :--- | :--- |
| **仅支持单节点 Redis** | 三条脚本无 hash tag，上集群会 `CROSSSLOT`。Redis 亦不得改用 `allkeys-lru` 等淘汰策略（会话键被淘汰 = AT 无法吊销） |
| **认证硬依赖 Redis** | 故障即全员 401 且无法登录；已在客户端配置 `timeout: 2s` / `connect-timeout: 1s` 避免请求挂死 |
| **令牌明文存储在 Redis** | AT/RT 以明文随机串存放在 Redis；32 字节随机串不可枚举，部署侧需收口 AOF 文件权限、禁 `MONITOR`、slowlog 策略 |
| **登出按 userId 吊销存在窄竞态** | 改成条件清理会让真正的登出退化成空操作，代价更大 |
| **单端登录** | 新登录覆盖旧会话（当前实现为单端） |
| **强制首次改密的豁免面是整个 `/auth/` 前缀** | 不是枚举清单。过滤器对 `permitAll` 端点同样执行，只豁免改密/登出/`me` 的话，用户连"刷新令牌""发本人验证码走通道 B 改密""忘记密码重置"都被挡住——AT 一过期就永远拿不到新令牌，**密码再也改不了**。前缀写法还让新增 `/auth` 端点自动豁免。判定用的是常量 `SecurityConstants.AUTH_MODULE_PREFIX`，与切面排除 `/api/logs` 是同一写法（`getRequestURI().startsWith(...)`）。另有 `OPTIONS` 一并放行——跨域预检不带业务语义，拦下它只会让前端在改密页上发不出请求。同理**不能**用 `shouldNotFilter()` 实现豁免：那会让过滤器对 `/auth/**` 整体失效，而 `/auth/me`、`/auth/logout`、`/auth/change-password`、`/auth/captcha`(CHANGE_PASSWORD) 都依赖它填 SecurityContext |
| **标志置 1 的三处、置 0 一处** | 置 1：`init.sql` 预置超管、Excel 导入、后台建号（共同点：口令由他人设定且对方已知）；自注册**不置**。置 0：`UserServiceImpl.updatePassword` 是改密与忘记密码重置的唯一写库入口，一处覆盖双通道 |

## 9. 本模块的高频坑（都踩过）

- **Lua 参数必须是字符串**：`StringRedisTemplate` 用 `StringRedisSerializer`，传 `Long`/`Integer`
  会在触达 Redis 前抛 `ClassCastException`（表现为登录全线 500）。调用侧统一 `String.valueOf(...)`，
  脚本内 `tonumber()`。
- **TTL 一律整数秒且下限为 1**：`SET ... EX 0` 报错，而 `EXPIRE key 0` 会**直接删键**。
- **配置里的 `Duration` 允许纯数字**：`max-lifetime: 30` 是 **30 毫秒**，不是 30 天。
  三个配置类（`AuthSessionProperties` / `CaptchaProperties` / `RbacCacheProperties`）都有启动期
  `@AssertTrue` 校验把这类配置挡在启动阶段——**新增带 `Duration` 的配置类时照做**，
  漏掉的表现是"缓存永不命中 / 验证码刚发就过期"，**零日志零报错**。
- **`AccessDeniedException` 与 401 的分工**：未登录走 `RestAuthenticationEntryPoint`（HTTP 401），
  已登录但无权限走 `RestAccessDeniedHandler` / 全局异常处理（HTTP 403）。
  另有一个例外：`/auth/captcha` 的 `CHANGE_PASSWORD` 场景未登录时返回 **HTTP 200 + body 401**
  （URL 层 permitAll，由业务层用 `SecurityUtils` 判定）。
