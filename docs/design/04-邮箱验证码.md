# 04 · 邮箱验证码

覆盖三个自助流程：**注册**、**忘记密码**、**修改密码（通道 B）**。登录不加验证码。

## 1. 接口一览

| 接口 | 类型 | 权限 | 说明 |
| :--- | :--- | :--- | :--- |
| `POST /auth/captcha` | 新增 | 匿名放行 | 发送验证码；`CHANGE_PASSWORD` 场景需登录，由业务层判定 |
| `POST /auth/register` | 改造 | 匿名 | 请求体增加 `captcha`（必填） |
| `POST /auth/forgot-password` | 新增 | 匿名放行 | 邮箱 + 验证码 + 新密码 ×2，成功后销毁全部会话 |
| `POST /auth/change-password` | 扩展 | 登录 | 双通道二选一：`oldPassword` / `captcha` |

## 2. Redis 五键

| Key | Value | TTL | 职责 |
| :--- | :--- | :--- | :--- |
| `qsx:auth:cap:{scene}:{email}` | 6 位数字（明文） | 5m | 验证码本体；同场景同邮箱重发即覆盖 |
| `qsx:auth:cap:attempt:{scene}:{email}` | 失败计数（INCR） | 与码同生共死 | 达到 `max-attempts` 即作废 |
| `qsx:auth:cap:limit:{scene}:{email}` | 发送间隔标记（`SET NX`） | 60s | 60 秒内只允许发一次 |
| `qsx:auth:cap:daily:{yyyyMMdd}:{scene}:{email}` | 当日发送计数 | 24h | 每日上限（默认 10 次） |
| `qsx:auth:cap:ipdaily:{yyyyMMdd}:{ip}` | 同 IP 当日发送计数（**跨场景、跨邮箱**） | 24h | 来源维度总上限（默认 30 次） |

**键里的 `{email}` 是折叠后的形态**：`CaptchaRedisKeys.normalizeEmail` 统一 `trim + toLowerCase`，
四个键构造器都先调它。原因是库为 `utf8mb4_general_ci`（比较大小写不敏感），而键是
**二进制精确匹配**的；不折叠就会出现「用大小写不同的邮箱发码 → 改密永久 1028」。
**新增任何以邮箱为键或为判据的逻辑，都要显式定义大小写口径。**

前缀常量唯一来源是 `CaptchaRedisKeys.PREFIX`（`qsx:auth:cap:`），
**测试清理清单也引用它**——新增键必须落在这个前缀之下，否则会跨用例残留。

四个设计点：

- **`{scene}:{email}` 双维度**：从结构上隔离三种场景，「注册码」不可能通过「改密」的校验。
- **`daily` 用日期串键而非裸键 + 滑动 TTL**：若每次发送都 `EXPIRE`，日限就退化成滑动窗口，
  持续调用者永远撞不到上限。
- **`attempt` 与码同生共死**：码过期即计数失效，不会出现「上一张码的失败次数卡住新码」。
- **`ipdaily` 是唯一能约束「单个来源总发送量」的口子**：邮箱维度的额度是「每个邮箱 10 次」，
  只按邮箱限流等于没限——换邮箱就有新额度，可被用来向任意地址群发，也是投递链被打爆的前提。
  它与其余四键的差别在于**没有邮箱维度**，
  且判定写在 `captcha_send.lua` 的**最前**：先读后判、命中即返回 `IP_QUOTA`，
  **不消费任何计数**（否则一次被拒的请求也会占用额度）。

## 3. 两条 Lua 脚本（`qsx-module-system/src/main/resources/lua/`）

> 脚本**必须与使用方同模块**（否则 `ClassPathResource` 加载失败），
> 两个 `DefaultRedisScript` Bean 必须用 `@Qualifier` 按名注入。

### 3.1 `captcha_send.lua` —— 发送（限流 + 落码 + 清零错次，一次原子完成）

```
① 先读 ipDailyKey（只读不写！）超限 → 'IP_QUOTA'   ← 放在最前，且**不消费任何计数**
② SET limitKey 1 NX EX gapTtl   失败 → 'GAP'（60s 内重复发送）
③ INCR dailyKey；仅当结果为 1 时 EXPIRE dailyTtl；超限 → 'QUOTA'
④ INCR ipDailyKey；仅当结果为 1 时 EXPIRE ipDailyTtl  ← 只统计**真正发出**的请求
⑤ SET codeKey code EX codeTtl；DEL attemptKey    ← 重新发码即重置错误计数
返回 'OK' | 'GAP' | 'QUOTA' | 'IP_QUOTA'
```

**为什么 IP 判定放在最前且只读**：被 IP 限额拒掉的请求不该有任何副作用——若先 `INCR` 再判，
一次被拒的调用也会占用该 IP 的额度（相当于自我加刑）；而放在最后则每次被拒都要白跑一遍
邮箱侧的全部写入。放在最前、只读一次，两个问题一起解决。

**为什么发送侧也必须原子**（而不是 Java 侧 `INCR` + `EXPIRE`）：拆开写会有两个静默故障——

1. `INCR` 成功而 `EXPIRE` 未执行（进程中断/连接断开）会留下**没有 TTL 的键**，
   该 `{scene}:{email}` 之后再也发不出验证码，且没有任何报错；
2. 每次发送都 `EXPIRE 86400` → 日限变滑动窗口，上限永不触发。

> 命中 `QUOTA` 时不回滚已占用的 limit 键（该用户今日已到顶，60 秒间隔已无意义）。
> `IP_QUOTA` 则相反：它在第 ① 步就返回，**那次请求什么都没写**，不留任何痕迹。

### 3.2 `captcha_verify.lua` —— 校验（比对 + 用后即焚 / 计数作废）

```
码不存在            → 'MISS'
相等                → DEL 两个键 → 'OK'（用后即焚）
不等                → INCR attempt；达到 maxAttempts → DEL 两个键 → 'LOCK'
返回 'OK' | 'MISS' | 'WRONG' | 'LOCK'
```

**为什么必须原子**：`GET → 比对 → INCR → DEL` 是非原子读改写，并发提交同一个码时双方都能
「校验通过」，用后即焚就成了空话（验证码可被双花）。

**返回码到业务码的映射（防探测）**：`MISS` 与 `WRONG` **统一**为
`1028 验证码无效或已过期`（不区分不存在/过期/填错，也不回显剩余次数——否则等于给爆破者一个进度条）；
`LOCK` → `1029 验证码错误次数超限，请重新获取`。

两端都是 **fail-closed**：Redis 异常一律向上抛（发送/校验均 500），与 `AuthSessionServiceImpl` 同策略。

## 4. 投递：`EmailService` 端口

业务层只注入 `EmailService` 接口，投递方式对它透明：

```java
public interface EmailService {
    void sendVerificationCode(CaptchaScene scene, String email, String code);
}
```

| 实现 | 装配条件 | 行为 |
| :--- | :--- | :--- |
| `SmtpEmailService` | `qsx.captcha.debug=false`（**或缺省**，`matchIfMissing=true`） | `@Async("captchaMailExecutor")` + `JavaMailSender`，投递到 `spring.mail.*` 指向的 SMTP |
| `DebugEmailService` | `qsx.captcha.debug=true` | 不投递，验证码随接口响应 `data.code` 直返；启动打 WARN 横幅 |

### 关键设计：两个实现按「行为是否真的不同」切，而不是按「环境」切

**Mailpit 本身就是真实的 SMTP 服务**（只是不外发），它与线上真实邮箱的差别只有 host/port/凭据——
这一层 `spring.mail.*` 已经在管了。所以 `SmtpEmailService` **一份代码同时服务本地与线上**，
想拆成 `MockEmailService` / `RealEmailService` 只会得到两份逐行相同的拷贝。

将来接真实服务商有两条路径：

- **对方是 SMTP**（QQ 企业邮、阿里云 SMTP 等）→ **只改 `spring.mail.*`，代码零改动**；
- **对方只提供 HTTP API**（SendGrid、阿里云邮件推送）→ 再加第三个实现
  （如 `XxxApiEmailService`）+ `@ConditionalOnProperty`，那时条件装配才真正承担「切实现」的职责。

> **两个实现的条件必须互斥**：都装配会启动即 `NoUniqueBeanDefinitionException`。
> 接口刻意只声明「发送验证码邮件」一个方法——将来要发通知邮件请另开方法或另建接口，
> 不要把它扩成万能发信器。

### 异步线程池

`captchaMailExecutor`（`qsx-framework/AsyncConfig`）：core 2 / max 4 / queue 16 / **`AbortPolicy`**。

- **独立于操作日志池**：邮件受外部 SMTP 影响，耗时不可控，与日志落库混用会互相拖累。
- **必须用 `AbortPolicy`，不能用 CallerRuns**（与日志池刻意相反）：CallerRuns 会把 SMTP 投递
  交给**请求线程**同步执行——一旦 SMTP 被 greylist / 限流 / 链路丢包，队列打满就等于
  Tomcat 线程被钉死在外部依赖上，**把"发信慢"放大成"全站不可用"**。
  「丢码比慢一拍更糟」这个直觉在这里是错的：丢的这一封由用户重发即可，
  而线程池打满没有任何用户能自救。
  被拒由 `CaptchaServiceImpl` 兜住并留 ERROR，码已落 Redis。
- **三个 SMTP 超时也必须显式配置**（`spring.mail.properties.mail.smtp.*`）：JavaMail 默认
  **无限等待**，是上面那条放大链的另一半。
- 上述两条都有配置测试固定（`MailChainConfigTest`），**改回默认值即转红**。
- `@Async` 靠 Spring 代理生效，**必须由外部 Bean 调用**（`CaptchaServiceImpl` → `EmailService`），
  同类内部自调用会让它静默失效（见 `OperationLogServiceImpl` 的教训）。
- **投递失败只记 ERROR 日志**：码已落在 Redis，用户重发即可，不该让接口报错。
  「接口返回成功」≠「邮件已送达」——本地看 `http://127.0.0.1:8025` 即可确认。

## 5. 三个场景的语义

| 场景 | 发码前置条件 | 说明 |
| :--- | :--- | :--- |
| `REGISTER` | 邮箱**必须未注册**（已注册 → 1001） | 注册流程本身必须告知邮箱被占用，无法隐藏 |
| `FORGOT_PASSWORD` | 邮箱**无论是否注册都返回同样的成功响应**；未注册时不落码、不投递 | 防枚举；顺带避免本接口被打成垃圾邮件发射器 |
| `CHANGE_PASSWORD` | **必须登录，且邮箱必须是本人**（否则 1032） | 本场景的码只能发到本人邮箱 |

- `/auth/captcha` 在 URL 层是 `permitAll`，但**认证过滤器照常执行**：带合法令牌时
  SecurityContext 里有身份，`CHANGE_PASSWORD` 的「登录 + 本人邮箱」才能在业务层判定；
  未登录时 `SecurityUtils` 抛 401，返回**body 业务码 401**（HTTP 仍是 200）。
- **防枚举的两个位置**：发送侧（未注册邮箱静默跳过）与重置侧（未注册邮箱必然落到与
  「码填错/过期」同一个 1028 与同一句文案）。

## 6. 业务侧接入：校验顺序统一为「前置条件 → 验证码」

```
注册：      Bean Validation → 邮箱唯一性 → 验证码校验 → 落库
忘记密码：  密码一致性(1030) → 验证码校验 → 反查用户 → 改密 → 销毁全部会话
修改密码：  二选一判定(1031) → 通道校验（原密码 1006 / 验证码 1028）→ 改密 → 销毁会话
```

**顺序不是随手定的**：验证码校验成功即用后即焚。放在唯一性之前，已注册邮箱的重试会把
用户手里那张有效的码烧掉（还得再等 60 秒才能拿新的）。这条在 `RegisterRequest` 与
`AuthServiceImpl.register` 的注释里都写明。

两个实现细节值得记：

- **1030 / 1031 在 Service 层判，不用 DTO 的 `@AssertTrue`**：DTO 校验失败会被统一压成
  笼统的 400，前端就没法把「两次密码打错」和「参数格式不对」分开提示。
- **改密的密码强度对齐了注册**（字母 + 数字）：改造前改密只校验 6-32 位长度，比注册还松，
  等于留了一条「用弱密码覆盖强密码」的路径。
- 忘记密码与改密成功后都调用 `AuthSessionService.remove`（与登出/踢人/禁用/删除同一收口）；
  失败只 ERROR 告警不阻断——密码已经改成功了，此时让接口报错反而让用户以为重置失败。

## 7. 配置项

```yaml
spring:
  mail:
    host: localhost        # 指向 Mailpit；上线换成真实 SMTP 只改这一段
    port: 1025
    username: ""           # Mailpit 不校验账号密码
    password: ""

qsx:
  captcha:
    debug: false           # true = 不投递，验证码随响应直返（仅本地联调！）
    ttl: 5m                # ⚠️ 纯数字会被当作毫秒：写 300 是 300 毫秒，不是 5 分钟
    max-attempts: 5
    send-interval: 60s
    daily-limit: 10                     # 每邮箱每日 10 次
    ip-daily-limit: 30                  # 每 IP 每日 30 次（跨场景、跨邮箱累计）
    from-address: no-reply@qsx.local   # 真实服务商多数要求发件地址已备案/校验
```

`spring.mail.properties.mail.smtp` 的三个超时（connectiontimeout / timeout / writetimeout）
也是**必配项**，理由见 §4 与 §10。

`CaptchaProperties` 有启动期 `@AssertTrue` 校验（`ttl` / `send-interval` 必须 ≥ 1 秒），
把「纯数字当毫秒」这类配置挡在启动阶段。

**安全边界**：

- `debug=true` 时任意调用者都能从响应里拿到验证码，**校验形同虚设**——仅限本地联调。
  **已落地**（2026-09）：`application-prod.yml` 显式 `debug: false`，并由 `ProdSecurityGuard`
  在 prod profile 启动期复检（`debug=true` 即拒绝启动，有 `ProdSecurityGuardTest` 固定）。
  本地不激活 prod，所以这条逃生口仍然保留。
- 通道 B（验证码改密）的本质是「**邮箱可达 = 凭据可改**」，靠「改密后统一销毁会话」止损。
- Mailpit 是本地假 SMTP，**生产必须接入真实邮件服务**。

## 8. 测试策略

| 关注点 | 做法 |
| :--- | :--- |
| 测试怎么拿到验证码 | **直读 Redis** `qsx:auth:cap:{scene}:{email}`，不依赖邮件。`BaseIntegrationTest.register()` 封装成「调发码接口 → 从 Redis 取码 → 带码注册」，各测试类的 `register(...)` 调用点无需关心验证码 |
| 发送间隔挡住同一用例内的二次发码 | helper 在拿不到码时删掉 `limit` 键重发一次（等价于真实用户等满 60 秒；用例不可能真的等） |
| 端到端投递 | `CaptchaMailSmokeTest`：发码 → 轮询 Mailpit API → 断言正文含同一个码；Mailpit 未启动时 `assumeTrue` 跳过 |
| 清理 | 验证码五键统一挂在 `qsx:auth:cap:` 前缀下，由 `BaseIntegrationTest` 的显式前缀清单在用例前后 SCAN 删除（否则限流计数与错次会跨用例残留） |
| 机制层断言 | 「用后即焚」要断言码键已删除、「错次作废」要断言码与计数都被清、「吊销即时生效」要断言 Redis 键消失——只断言业务码会被「每请求查库兜底」掩盖 |

## 9. 决策记录

| # | 决策 | 结论 |
| :--- | :--- | :--- |
| D1 | 发送通道 | Mailpit 真实投递为主（`JavaMailSender` + `@Async`），`qsx.captcha.debug=true` 降级为响应直返 |
| D2 | 后台建号（`POST /api/users`）要不要验证码 | **不要**，走既有 `user:create` 鉴权；验证码只服务自助流程 |
| D3 | 忘记密码/改密成功后是否自动登录 | **不自动登录**，前端引导重新登录 |
| D4 | 验证码规格 | 6 位数字 · 5 分钟 · 错 5 次作废 · 用后即焚 |
| D5 | 改密成功后是否销毁会话 | **统一销毁**（保持六入口收口一致） |
| D6 | 存储维度 | Redis，`{scene}:{email}` 双维度 |
| D7 | 键前缀 | `qsx:auth:cap:*`（认证域统一命名空间） |
| D8 | 注册校验顺序 | 唯一性**先于**验证码（不误烧用户的码） |
| D9 | 异步线程池拒绝策略 | ~~小队列 + `CallerRunsPolicy`（宁慢不丢）~~ → **小队列 + `AbortPolicy`（宁丢不拖垮全站）**，**2026-09 修订**，理由见 §10 |

> D5 的理由值得单独记：改密是**止损事件**（旧密码可能已泄露），继续沿用已签发令牌会让改密
> 失去意义；且本系统是单端登录，销毁的代价只是「本人重登一次」，而 refresh 链路不看密码，
> 不销毁的话已流出的 RT 最长还能续期到 30 天绝对上限。

## 10. 邮件链与限流加固

- **新增第 5 个键** `qsx:auth:cap:ipdaily:{yyyyMMdd}:{ip}`：同 IP 当日发送上限（默认 30，`qsx.captcha.ip-daily-limit`）。
  只按邮箱限流等于没限——换邮箱即有新额度，而这是唯一"往任意地址发信"的公开接口。
  判定与自增都在 `captcha_send.lua` 内（KEYS[5]/ARGV[6]），且**先读后判、超限即返回，不消费任何计数**；
  IP 计数只统计真正发出去的请求（放在邮箱侧校验之后），避免 NAT 后的正常用户被"被拒的重试"误伤。
- **SMTP 三个超时**（connectiontimeout / timeout / writetimeout = 5000）必须显式配置：JavaMail 默认无限等待。
- **邮件池改 `AbortPolicy`**：CallerRuns 会让请求线程同步做 SMTP，队列打满即线程池打满、全站不可用；
  被拒的 `RejectedExecutionException` 在提交时刻抛出（异步方法还没进去），由 `CaptchaServiceImpl` 兜住并留 ERROR，
  码已落 Redis，用户重发即可（代价是等满 60 秒发送间隔）。两条决策由 `MailChainConfigTest` 固定。
