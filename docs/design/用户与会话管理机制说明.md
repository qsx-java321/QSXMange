## 2. 总体设计：一套统一会话机制 + 面向他人的管理

本项目不是一个「用户自我中心」系统，而是一个**后台管理系统**。因此必须分清两类身份的职责：

- **普通用户**（无角色 / 无 `user:*` 权限码）：只能走认证自我接口，不能管理他人。
- **管理员**（持有 `user:*` 权限码，ADMIN 超管因绑定全量权限码而天然全量）：对**其它账号**做增删改查、分配角色、踢下线。

会话机制对两类身份**完全一致**——这决定了「登出、踢人、禁用、删除、改密都会让目标令牌立即失效」是统一保证的。

## 3. 会话管理（对所有人统一）

### 3.1 双 Token + Redis 三键模型

无 JWT。access token（AT）与 refresh token（RT）都是 32 字节 SecureRandom 的 hex 随机串，无签名无载荷，**Redis 是令牌有效性的唯一真相源**：

| Key | Value | TTL | 职责 |
|:---|:---|:---|:---|
| `qsx:auth:at:{at}` | userId | 30m | AT 有效性；删除即吊销 |
| `qsx:auth:rt:{rt}` | userId | 7d | RT → userId；轮换时删旧立新 |
| `qsx:auth:session:{userId}` | Hash{accessToken, refreshToken, firstLoginTs} | 7d 滑动 | 单端覆盖、按用户清理、绝对上限 |

所有多键操作走 Lua 原子脚本（`SessionLuaTest` 直连验证原子性与并发双花）。

### 3.2 认证请求链路（每请求）

`TokenAuthenticationFilter`（Redis 反查 userId）→ `SecurityUserDetailsService.loadUserById`（实时查库 + 权限）→ `isEnabled()`（status==0 才放行）→ 写入 SecurityContext。

> 关键：即使「禁用分支的会话清理漏写」，每次请求实时查库的 `isEnabled()` 也会兜底拒绝。因此测试不只断言 401，还要断言 Redis 键已消失（防兜底掩盖漏实现）。

### 3.3 令牌生命周期

- **登录** `/auth/login` → `issue()`：生成 AT/RT，Lua 原子写三键；**单端登录**（新登录覆盖旧会话，旧 AT/RT 立即失效）。
- **刷新** `/auth/refresh`（入参仅 `{refreshToken}`）→ `rotate()`：**严格轮换**，旧 RT 一经使用立即失效（重放返回 1019）；30 天绝对上限用 `firstLoginTs` 判定，轮换不续命；除缺参返回 400 外的一切刷新失败统一 1019。
- **登出** `/auth/logout` → `remove()` 清三键。
- **改密** `/auth/change-password` → 改密码库 + 清会话（强制重新登录）。

### 3.4 统一回收入口 `remove(userId)` —— 本设计最关键的一环

登出、踢人、禁用、删除、改密，最终都收敛到 `AuthSessionService.remove(userId)` 清掉 at/rt/session 三键，令令牌立即失效。

- 删除 / 禁用等写操作走 **AFTER_COMMIT** 清理：事务回滚时不给「其实没被删的用户」登出。
- 会话层 Redis 故障 **fail-closed**（拒绝认证，宁可不放行）；权限缓存层 **fail-open**（Redis 异常降级查库）。两边界不混淆。

### 3.5 权限缓存

`qsx:auth:perm:{userId}`（TTL 30m，空权限也回填防穿透）。用户角色/权限一变 → 事务内 `publishEvent(PermissionCacheEvictEvent)` → `@TransactionalEventListener(AFTER_COMMIT)` 精确删键，下次请求实时回源，保证「权限变更即时生效」。

## 4. 用户管理（管理员视角）

### 4.1 权限闸门

`@PreAuthorize("hasAuthority('user:xxx')")`。ADMIN 超管通过绑定全量权限码实现（非硬编码 `hasRole`）；普通用户调 `/api/users/**` 一律 403。

### 4.2 接口流程

| 接口 | 权限码 | 服务方法 | 关键流程 |
|------|--------|---------|---------|
| `GET /api/users` | user:page | `page` | email/nickname 模糊 + status 精确，id 倒序 |
| `GET /api/users/{id}` | user:get | `getById` | 不存在 → 1004 |
| `POST /api/users` | user:create | `create` | 邮箱唯一(1001) → BCrypt 加密 → status 限 0/1；弱密码/非法邮箱/昵称>50 由 DTO `@Valid` 拦为 400 |
| `PUT /api/users/{id}` | user:update | `update` | 改邮箱唯一（排除自身）；**status「非 0 即禁用」**→ 若禁用则受保护 + 清会话踢下线；普通编辑(status=0)不清会话 |
| `DELETE /api/users/{id}` | user:delete | `delete` | 删自己(1022)/删超管(1025) 保护 → email 加 `#deleted_<ts>` 释放唯一索引 → 逻辑删除(deleted=1) → 提交后清会话 + 失效缓存 |
| `PUT /api/users/{id}/roles` | user:assign-role | `assignRoles` | 校验 user(1004)/role(1009) → 整表替换（物理删旧 + 批量插新）→ 提交后失效权限缓存即时回收；空 `roleIds` = 清空角色 |
| `POST /api/users/{id}/kick` | user:kick | `kick` | 踢自己(1022)/踢超管(1021) 保护 → 清目标三键（AT 立即 401），账号本身不受影响可重登 |

### 4.3 保护矩阵（管理员对目标账号操作）

> `delete` 已补齐为 1025 / 1022，与禁用、踢人完全对称。**超管和自己永远不受普通管理动作触碰。**

| 操作 | 普通用户 | 内置超管 ADMIN | 自己 |
|------|---------|--------------|------|
| 删除 | 允许 | ✗ 1025 | ✗ 1022 |
| 禁用 | 允许 | ✗ 1020 | ✗ 1022 |
| 踢下线 | 允许 | ✗ 1021 | ✗ 1022 |

> 判定谓词统一为「status 非 0 即禁用」，与 `SecurityUser.isEnabled()`、`AuthServiceImpl.refresh` 兜底用同一谓词，避免「按 A 谓词禁用、按 B 谓词清理」的错位。

#### 保护矩阵的成立前提：身份判定 ≠ 授权判定

上表三条保护判定「目标是不是内置超管」走 `UserMapper.existsRoleCode(userId, "ADMIN")`——该查询**刻意不过滤 `sys_role.status`**，与授权查询 `selectRoleCodes`（带 `AND r.status = 0`）分工严格区分：

| 查询 | 回答的问题 | 是否过滤角色状态 |
|------|-----------|----------------|
| `selectRoleCodes` / `selectPermissionCodes` | 该用户**实际拥有**哪些权限 | **是**（停用角色不授权，正确语义） |
| `existsRoleCode` | 该用户**是不是**某个内置身份 | **否**（身份不因角色被停用而改变） |

**语义错位的后果**：曾用 `selectRoleCodes(id).contains("ADMIN")` 做身份判定，两者复用同一条查询——`ADMIN` 角色一旦被停用，该查询返回空集，`.contains("ADMIN")` 恒为 false，**1020/1021/1025 三条保护同时静默失效**，操作者随即可以禁用/删除/踢掉超管账号。这与 `isDisabling` 是同一类教训：判定谓词必须与它要回答的问题同源。

#### 内置超管角色不可停用（1026）

`RoleServiceImpl.update` 在实体变更**之前**拦截停用 `ADMIN` 角色的请求。停用后所有「仅经 `ADMIN` 角色获得权限」的用户立即失去全部权限码（含分配权限所需的 `role:update` / `role:assign`），若此时无人持有其它带 `role:update` 的角色，就再没有人能通过接口把它启用回来，系统被锁死在「无人可管理权限」的状态，只能直接改库恢复。与 `delete()` 的「超管角色不可删除」对称：**一个防删、一个防停，都是防系统失控**。

两道闸的分工：1026 拦住接口路径；`existsRoleCode` 是第二道闸，即使角色已因历史数据或直接改库而处于停用态，保护依然成立。

## 5. 普通用户 vs 管理员：能力边界

**普通用户（只走 `/auth/*`，无 `user:*`）：**
- 登录 `/auth/login`、刷新 `/auth/refresh`、登出 `/auth/logout`
- 看自己 `/auth/me`、改自己密码 `/auth/change-password`（改后会话清空强制重登）
- 按角色权限访问业务接口；调 `/api/users/**` → 403

**管理员（持 `user:*`，ADMIN 天然全量）：**
- 对其它账号完整增删改查、分配角色、踢下线、批量导入导出
- 保留全部 `/auth/*` 自我接口
- 受 4.3 对称保护：不可删/禁/踢超管、不可删/禁/踢自己

## 6. 边界与工程要点（踩坑沉淀）

- **Lua 参数必须字符串化**（`StringRedisTemplate` + StringRedisSerializer，传 Long 会 ClassCastException），脚本内 `tonumber()`。
- **Lua 读 Hash 用 `HGET` 而非 `HGETALL`**（RESP2 下返回数组而非 map，字段访问恒 nil）。
- **Lua 写序固定先清旧 → 写 session → 写令牌键**（报错不回滚，崩溃留死令牌而非不可吊销裸令牌）。
- **删除释放邮箱**：逻辑删除前将 email 拼 `#deleted_<ts>`，避免与唯一索引冲突，允许同邮箱再注册。
- **会话脚本仅支持单节点 Redis**（无 hash tag，上集群会 CROSSSLOT）；Redis 不得改 `allkeys-lru` 淘汰（会话键被淘汰 = AT 无法吊销）。
- **测试隔离**：只清 `email LIKE '%@test.com%'` 的测试用户，禁用全表删除（会删内置超管）；测试清空 `qsx:auth:*` 与会话键。
