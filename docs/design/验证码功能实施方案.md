## 0. 与旧参考稿的差异（本次核对后的修订）

旧稿的结构与决策（D1~D6）基本可用，但下列 9 处经代码核对必须修订，否则会在第一步就编译不过或让测试基线大面积转红：

| # | 旧稿写法 | 问题 | 本文档的修订 |
| :--- | :--- | :--- | :--- |
| 1 | `spring-boot-starter-mail` 加在 `qsx-admin` pom | 依赖方向是 `qsx-admin → qsx-module-system`，**反向取不到 `JavaMailSender`，邮件实现类编译失败** | 依赖加在 `qsx-module-system` |

| 5 | 未提测试清理 | `BaseIntegrationTest` 按**显式前缀清单**清理，`qsx:cap:*` 不在其中 → 验证码/计数跨用例残留，限流与「错 5 次作废」类用例随机转红 | 新增前缀常量并**加入清理清单**（注意：现有清理不是 `qsx:auth:*` 通配，是 4 个显式前缀） |
| 6 | 注册顺序：密码一致 → **验证码** → 邮箱唯一 | 已注册邮箱重试会把用户的有效码**误烧**；且既有用例 `register_duplicateEmail` 会从 1001 变成验证码错误 | 顺序改为：密码一致 → **邮箱唯一** → 验证码 → 落库 |
| 7 | §7.3 / §12.1 称「`qsx-security` 零内核改动」 | 与 §4.1 自相矛盾——白名单就写在该模块 | 明确为「改 `qsx-security` 的 2 个常量 + 1 行白名单」 |

| 9 | 「生产 profile 下 debug=true 启动即拒」 | 本地阶段收益为零、噪音大 | 降级为**启动 WARN 日志 + 文档红线**（真上线前再收紧为拒止） |

## 1. 决策基线

沿用旧稿已确认的 D1~D6，并补 3 条本轮新增决策：

| :--- | :--- | :--- | :--- |

## 2. Redis 键与 Lua 脚本

### 2.1 键设计

| Key | Value | TTL | 职责 |
| :--- | :--- | :--- | :--- |
| `qsx:auth:cap:{scene}:{email}` | 6 位数字（明文） | 300s | 验证码本体；同场景同邮箱重发即覆盖 |
| `qsx:auth:cap:attempt:{scene}:{email}` | 失败次数（INCR） | 300s | 与码同生共死；≥5 作废 |
| `qsx:auth:cap:limit:{scene}:{email}` | 发送间隔标记 | 60s | 60s 内只允许发 1 次 |
| `qsx:auth:cap:daily:{yyyyMMdd}:{scene}:{email}` | 当日发送计数 | 86400s | 日上限 10 次；日期串键天然滚动，无滑动窗口问题 |

`scene ∈ {REGISTER, FORGOT_PASSWORD, CHANGE_PASSWORD}`，与 `attempt/limit/daily` 无命名冲突。key 构造器统一放 `CaptchaRedisKeys`（对齐 `AuthRedisKeys` 的写法：前缀常量单一来源）。

### 2.2 `captcha_send.lua`（发送：限流 + 落码 + 清零错次，一次原子完成）

```
KEYS[1]=code 键  KEYS[2]=attempt 键  KEYS[3]=limit 键  KEYS[4]=daily 键
ARGV[1]=code  ARGV[2]=codeTtl  ARGV[3]=gapTtl  ARGV[4]=dailyTtl  ARGV[5]=dailyLimit
返回：'OK' | 'GAP' | 'QUOTA'
```

- `SET limitKey 1 NX EX gapTtl` 失败 → 返回 `GAP`（60s 内重复发送）
- `INCR dailyKey`，**仅当结果为 1 时** `EXPIRE dailyTtl`；超过 `dailyLimit` → 返回 `QUOTA`
- `SET codeKey code EX codeTtl` + `DEL attemptKey`（**重新发码即重置错次**）

> 命中 `QUOTA` 时不回滚已占用的 limit 键（该用户今日已到顶，60s 间隔无意义）。这是有意的简化，不引入回滚复杂度。

### 2.3 `captcha_verify.lua`（校验：比对 + 用后即焚 / 计数作废）

```
KEYS[1]=code 键  KEYS[2]=attempt 键
ARGV[1]=输入码  ARGV[2]=maxAttempts  ARGV[3]=codeTtl
返回：'OK' | 'MISS' | 'WRONG' | 'LOCK'
```

- 码不存在 → `MISS`
- 相等 → `DEL` 两个键 → `OK`（用后即焚）
- 不等 → `INCR attempt`，**仅当结果为 1 时** `EXPIRE codeTtl`；达到 `maxAttempts` → `DEL` 两个键 → `LOCK`

**返回码到业务码的映射（防探测）**：`OK` → 成功；`MISS` 与 `WRONG` **统一**「验证码无效或已过期」（不区分不存在/过期/填错，也不回显剩余次数）；`LOCK` → 「错误次数超限，请重新获取」。

### 2.4 工程约定（照抄会话脚本的红线）

- 脚本参数**全为字符串**（`String.valueOf(...)`），脚本内 `tonumber()`；`StringRedisSerializer` 传 Long 会在触达 Redis 前抛 `ClassCastException`。
- Lua 脚本**必须与使用方同模块**：本次落 `qsx-module-system/src/main/resources/lua/`，否则 `ClassPathResource` 加载失败。
- 脚本 Bean 用 `DefaultRedisScript` + `@Qualifier` 注入（同类型多 Bean，按类型注入会 `NoUniqueBeanDefinitionException`）；`DefaultRedisScript` **只校验文件存在、不校验语法**，语法错误要到首次 `EVAL` 才暴露 → 必须有真的执行两条脚本的测试。
- **fail-closed**：Redis 异常一律向上抛（send → 500；verify → 500），与 `AuthSessionServiceImpl` 同策略，不降级放行。
- 不读 Hash、不涉及多键跨 slot 之外的问题；单节点 Redis 前提不变。

## 5. 流程设计

### 5.1 `POST /auth/captcha`（新增，`permitAll`）

```
① 参数校验：scene 必须为合法枚举；email 格式合法（非法 → 400）
② 场景前置条件：
   REGISTER         → 邮箱必须【未注册】（已注册 → 1001）
   FORGOT_PASSWORD  → 邮箱【无论是否注册都返回同样的成功响应】（防枚举，见下）
   CHANGE_PASSWORD  → 必须携带有效登录态（否则 401）；且 email 必须等于当前登录用户邮箱（否则 1032）
③ captchaService.send(scene, email)
   → GAP/QUOTA → 1027；成功 → 落码 + 异步投递
④ 返回：debug=true → data={code}；否则 data=null（提示「验证码已发送」）
```

- **`/auth/captcha` 是 `permitAll`，但认证过滤器照常执行**：客户端带 token 时 SecurityContext 有身份，`CHANGE_PASSWORD` 场景的「必须登录 + 邮箱=本人」才能在 Service 层判定；不带 token 则该场景返回 401（已实测：`permitAll` 路径上过滤器仍会跑一次 Redis 反查）。
- **防枚举的不对称性（有意保留）**：`REGISTER` 对已注册邮箱返回 1001——注册流程本身就要求告知「邮箱已被占用」，无法隐藏；`FORGOT_PASSWORD` 则必须对未注册邮箱返回与成功**完全一致**的响应（同 HTTP 状态 + 同业务码 + 同文案）。短信/邮件验证码场景的标准取舍，写进接口文档。
- `CHANGE_PASSWORD` 前置条件即「通道 B 的发送权限」，即本场景的码只能发到本人邮箱。

### 5.2 注册改造（`POST /auth/register`）

```
① Bean Validation（含 captcha @NotBlank、密码强度、邮箱格式）
② 邮箱唯一性（现状逻辑，1001）
③ captchaService.verify(REGISTER, email, captcha)   ← 不通过：1028 / 1029
④ BCrypt + 落库（现状）
⑤ 不签发令牌（维持「注册后手动登录」）
```

顺序见 D8：唯一性在验证码之前，已注册邮箱不会烧掉用户的码。

### 5.3 忘记密码（新增 `POST /auth/forgot-password`，`permitAll`）

```
① Bean Validation（newPassword 强度 + confirmPassword 一致，不一致 → 1030）
② captchaService.verify(FORGOT_PASSWORD, email, captcha)   ← 未注册邮箱无码可比 → 1028（与过期同文案，天然不泄露注册状态）
③ 反查 email → userId（getByEmail，@TableLogic 过滤已删用户）；查不到 → 1028
④ BCrypt 加密 → userService.updatePassword(userId, encoded)
⑤ authSessionService.remove(userId)   ← 统一销毁（D5），失败 ERROR 告警不阻断
⑥ 返回成功，不自动登录（D3）
```

### 5.4 改密双通道（`POST /auth/change-password`，需登录）

| 通道 | 校验 | 失败码 |
| :--- | :--- | :--- |
| A（现状保留） | `oldPassword` BCrypt 匹配 | 1006 |
| B（新增） | `captchaService.verify(CHANGE_PASSWORD, 当前用户邮箱, captcha)` | 1028 / 1029 |

```
① 二选一校验：两者都传或都不传 → 1031（DTO 用 @AssertTrue 或 Service 层判定，取 Service 层）
② 通过后落库 → ③ authSessionService.remove(id)（统一销毁，失败 ERROR 不阻断）
```

- 通道 A 行为与现状**完全一致**，不改变既有语义。
- 通道 B 的安全边界需在接口说明中明示：**邮箱可达 = 凭据可改**；靠「改密后统一销毁会话」止损。

## 6. 配置项

```yaml
spring:
  mail:                       # Mailpit（本地假 SMTP，见 docs/dev-env/组件依赖README.md）
    host: localhost           # 该 Bean 不存在会导致启动失败，勿删
    port: 1025
    username: ""              # Mailpit 不校验账号密码
    password: ""

qsx:
  captcha:
    debug: false              # true = 不投递、响应直返 code（仅本地联调）
    ttl: 5m                   # 验证码有效期
    max-attempts: 5           # 错几次作废
    send-interval: 60s        # 同场景同邮箱发送间隔
    daily-limit: 10           # 同场景同邮箱每日上限
```

`CaptchaProperties` 用 `@Validated` + `@AssertTrue` 做启动期校验（对齐 `AuthSessionProperties` 的防呆风格：**纯数字会被当毫秒**，`ttl: 300` 是 300 毫秒不是 5 分钟）。`debug=true` 时打一条 WARN 横幅日志（修订点 #9）。

## 7. 测试方案

### 7.1 取码方式（修订点 #4）

`BaseIntegrationTest.register()` 改造为**真实走发码接口 + 直读 Redis 取码**：

```
register(email, password):
  ① POST /auth/captcha {REGISTER, email}      // 忽略返回值：邮箱已注册 / 触发限流时拿不到码
  ② String code = redis.get("qsx:auth:cap:REGISTER:" + email)
  ③ code = (code != null ? code : "000000")   // 兜底：走唯一性分支的场景本就不需要真码
  ④ POST /auth/register {email, password, captcha: code}
```

这样做的收益：**8 个测试类里的几十处 `register(...)` 调用点一行都不用改**（`AuthRefreshTest` / `AuthSessionTest` / `BusinessFlowTest` / `UserImportExportTest` / `UserEdgeTest` / `RbacTest` 等全部无感），且测试**不依赖 Mailpit**（投递是异步的，Mailpit 挂了也只是异步线程记一条错误日志）。

### 7.2 清理扩展（修订点 #5）

`BaseIntegrationTest` 的清理是**显式前缀清单**（`qsx:auth:perm:` + `at`/`rt`/`session`，用 SCAN 删除），不是 `qsx:auth:*` 通配。新增 `CaptchaRedisKeys.PREFIX`（`qsx:auth:cap:`）并加入该清单，前后各清一次；否则「错 5 次作废」「60s 限流」「重发覆盖」类用例会被上一条用例的残留计数污染。

## 9. 风险与有意取舍

| # | 风险 | 处置 |
| :--- | :--- | :--- |
| R1 | `debug=true` 时验证码形同虚设（响应直返 code） | 默认 false；启动 WARN；文档红线（本地阶段不引入生产启动拒止，见修订点 #9） |
| R2 | 邮箱失守 = 密码失守（验证码改密的本质） | 接口说明明示边界；改密/重置后统一销毁会话止损 |
| R3 | `REGISTER` 发码接口对已注册邮箱返回 1001（枚举 oracle） | 注册流程本身必须告知邮箱占用，无法隐藏；`FORGOT_PASSWORD` 侧严格防枚举。写进接口文档，不视为缺陷 |
| R4 | 跨场景复用 | key 双维度 + `verify` 必须显式传 scene |
| R5 | 重放 / 爆破 | 用后即焚 + 错 5 次作废 + 间隔/日限 |
| R6 | 异步投递失败（Mailpit 未启动） | 接口仍返回成功（**发送成功 ≠ 邮件已到**，接口文档明示）；异步线程记 ERROR 日志；本地看 8025 即可判断 |
| R7 | 既有 171 例基线 | 迁移清单先行（§7），`register()` helper 改造把改动面收敛到 1 个方法 + 1 个测试类 |

**本地阶段的简化（有意不做）**：生产启动拒止、投递失败重试/死信、HTML 邮件模板与国际化、发送 IP 维度限流。这些在切生产前再补，不影响本方案的接口与数据设计。

## 10. 明确不做（Out of Scope）

- 登录验证码 / 图形验证码 / 滑块：**不做**
- 后台管理员建号（`POST /api/users`）与 Excel 导入的验证码：**不做**（走既有权限码鉴权）
- 多端登录 / 多会话改造：**不做**
- 真实邮件服务商投递：**本轮不接**（`EmailService` 端口已隔离：SMTP 服务商只改 `spring.mail.*`；HTTP API 服务商再加一个实现）
