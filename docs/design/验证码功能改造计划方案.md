## 1. 背景与目标

### 1.1 现状

- 注册仅需邮箱 + 密码；登录为邮箱 + 密码；修改密码仅支持「旧密码 + 新密码」单通道（`AuthServiceImpl.changePassword`）。
- 会话体系为 Redis 有状态双 token（AT/RT/session 三键），「登出 / 踢人 / 禁用 / 删除 / 改密」五入口统一收口 `AuthSessionService.remove(userId)` 实现「吊销即时生效」。
- 认证链路 **fail-closed**（Redis 故障 → 拒绝认证），权限缓存 **fail-open**（降级查库）。

### 1.2 目标

1. 新增**通用验证码服务**（发送 / 存储 / 校验三合一），供多个自助流程复用。
2. **注册**增加邮箱验证码校验（邮箱 + 验证码 + 密码 ×2）。
3. **忘记密码**新增匿名重置通道（邮箱 + 验证码 + 新密码 ×2），重置成功后强制销毁该用户会话。
4. **修改密码**扩展为双通道：通道 A「旧密码 + 新密码」（现状保留），通道 B「验证码 + 新密码」（新增，仅需登录态）；任一通道成功即统一销毁会话（强制下线）。
5. 登录保持现状（邮箱 + 密码），不引入验证码。

### 1.3 明确不做的范围（Out of Scope）

- 登录验证码 / 图形验证码 / 滑块验证码：**本次不做**。
- 后台管理员创建用户（`POST /api/users`）验证码：**不做**（已确认，走既有 `user:create` 权限鉴权，验证码仅服务自助流程）。
- 真正的邮件投递（RabbitMQ + 邮箱）：**本次不做**，仅预留端口抽象；当前采用「验证码直接返回前端」的调试直返模式（见 §3.3 安全债）。
- 多端登录 / 多会话会话体系改造：**不做**。

## 2. 决策记录（已确认，定稿基线）

| # | 决策项 | 结论 | 说明 |
| :--- | :--- | :--- | :--- |
| D1 | 验证码 debug 直返管控 | **先直返，接邮件时再补开关** | 本地开发阶段可接受；接邮件时须补 debug 开关与生产强校验（启动即拒） |
| D2 | 后台创建用户是否需验证码 | **不需要** | 仅自助流程需要 |
| D3 | 忘记密码 / 验证码改密成功后是否自动登录 | **不自动登录** | 与现有注册/改密语义一致，引导重新登录 |
| D4 | 验证码失效 / 尝试策略 | **6 位 · 5min · 错 5 次作废 · 用后即焚** | 校验成功立即删除，防止重放 |
| D5 | 改密成功后是否销毁会话 | **统一销毁（保持现状）** | 含通道 A 与通道 B、忘记密码重置；五入口收口一致 |
| D6 | 验证码存储 | Redis，key 绑定 `{scene}:{email}` 双维度 | 防止跨场景复用 |

**D5 设计意图（记录原因）**：

- 改密视为「止损事件」（password rotation ≈ security incident）：旧密码可能已泄露，继续沿用已签发令牌会让改密失去止损意义。
- 本系统为**单端登录（单会话）**：销毁会话的代价仅「本人重登一次」，无多设备牵连；而 `refresh` 链路无密码兜底（只看 deleted/status），若不销毁、已流出 RT 最长可续期至 30 天绝对上限。
- 五入口（登出/踢人/禁用/删除/改密）统一收口是本项目的招牌保证，不单独为改密开例外。

## 3. 验证码服务设计

### 3.1 场景枚举

```java
public enum CaptchaScene {
    REGISTER,            // 注册
    FORGOT_PASSWORD,     // 忘记密码
    CHANGE_PASSWORD      // 修改密码（通道 B）
}
```

- Redis key 一律为 `qsx:cap:{scene}:{email}`（双维度绑定，杜绝「注册码用于改密」类跨场景复用）。
- `scene` 作为 key 一部分，**任何校验都必须带 scene**，从结构上隔离三种验证码。

### 3.2 Redis 存储与脚本

| Key（规划） | Value | TTL | 职责 |
| :--- | :--- | :--- | :--- |
| `qsx:cap:{scene}:{email}` | `{code}`（6 位数字，明文） | 300s（5min） | 验证码本体；同场景同邮箱重复发送时覆盖旧码 |
| `qsx:cap:attempt:{scene}:{email}` | 尝试失败次数（INCR） | 300s | 与验证码同步 TTL；≥5 次即作废 |
| `qsx:cap:limit:{scene}:{email}` | 发送频率计数（INCR） | 60s | 60s 内限 1 次 |
| `qsx:cap:daily:{scene}:{email}` | 当日计数（INCR） | 86400s | 每日上限（规划默认 10 次） |

> **多键校验必须走 Lua 原子脚本**（复用项目既有约定：Lua 脚本与使用方同模块、参数必须字符串、脚本内 `tonumber()`）。
> 建议脚本能力：`GET code → 比对 → 成功则 DEL 两个 key（用后即焚）/ 失败则 INCR attempts（超限则 DEL）`，消除「GET → 改 → SET」非原子读改写竞态。

### 3.3 发送通道：端口抽象（渐进演进）

沿用项目「端口 + 依赖倒置」风格（参考 `qsx-security` 的 `port` 包），发送通道抽象为端口，当前以调试直返实现，后续替换为 RabbitMQ + 邮件：

```java
// 发送端口：职责仅为「投递」，投递方式由实现决定
public interface CaptchaSender {
    void send(CaptchaScene scene, String email, String code);
}

// 实现一（当前）：调试直返——不投递，由 Service 将 code 拼入响应 data 返回前端
@Component
public class DebugCaptchaSender implements CaptchaSender {
    public void send(CaptchaScene scene, String email, String code) { /* no-op */ }
}

// 实现二（未来，本方案不实现）：RabbitMQ 消息 → 邮件服务真正投递
// public class MailCaptchaSender implements CaptchaSender { ... }
```

**安全债声明（必读）**：Debug 直返模式下，任意调用者可自行构造请求拿到验证码，**校验形同虚设**。本方案将该风险标记为**已接受的安全债**，仅允许在本地开发阶段使用；**接邮件通道时必须**：
1. 新增配置项 `qsx.captcha.debug`（默认 false）；
2. 生产环境启动校验：`debug=true` 直接拒绝启动；
3. 直返期间禁止用于任何非本地环境。

### 3.4 发送流程（规划）

```
POST /auth/captcha  {scene, email}
  ├─ ① 参数校验：scene 合法；email 格式合法
  ├─ ② 场景前置条件：
  │     REGISTER          → 邮箱必须【未注册】（getByEmail == null，否则 1001）
  │     FORGOT_PASSWORD   → 邮箱必须【已注册】（否则统一提示文案，防枚举，见 §5）
  │     CHANGE_PASSWORD   → 需登录，且 email 必须等于当前登录用户邮箱（否则 403/400）
  ├─ ③ 限流：cap:limit INCR；cap:daily INCR（超限 → 发送过于频繁业务码）
  ├─ ④ 生成 6 位数字码 → SET cap:{scene}:{email}
  ├─ ⑤ sender.send(scene, email, code)
  └─ ⑥ 返回：debug 模式 data={code}；否则 data=null（提示「验证码已发送」）
```

### 3.5 校验流程（规划，Lua 原子）

```
verify(scene, email, code)
  ├─ GET qsx:cap:{scene}:{email} → 不存在 → 返回「验证码无效或已过期」
  ├─ code 不匹配 → INCR attempts；>=5 → DEL 作废；否则返回「验证码错误」
  └─ code 匹配 → 立即 DEL 验证码与计数 key（用后即焚）→ 成功
```

**fail 策略**：验证码链路与认证一致采用 **fail-closed**——Redis 故障时发送 / 校验一律拒绝（不降级放行），与 `AuthSessionServiceImpl` 保持同策略。

## 4. 四个流程改造明细

### 4.1 接口清单总览

| 接口 | 类型 | 场景/权限 | 说明 |
| :--- | :--- | :--- | :--- |
| `POST /auth/captcha` | 新增 | 匿名（白名单） | 发送验证码；debug 模式直返 code |
| `POST /auth/register` | 改造 | 匿名 | 增加 `captcha` 字段 |
| `POST /auth/login` | 不变 | 匿名 | 邮箱 + 密码（可选增强：失败次数限制，见 §10） |
| `POST /auth/forgot-password` | 新增 | 匿名（白名单） | 验证码重置密码，成功后销毁会话 |
| `POST /auth/change-password` | 扩展 | 需登录 | 双通道二选一，成功后销毁会话 |
| `POST /auth/logout` / `GET /auth/me` / `POST /auth/refresh` | 不变 | — | 不受影响 |

**Security 白名单调整**（`SecurityConfig` / `SecurityConstants`）：`/auth/captcha`、`/auth/forgot-password` 加入 permitAll，与既有 `REGISTER/LOGIN/REFRESH` 并列。

### 4.2 注册改造（`POST /auth/register`）

- **请求体**（规划 `RegisterRequest` 扩展）：`{email, captcha, password, confirmPassword}`。
- **流程**：

```
register(request)
  ├─ ① password == confirmPassword 校验（Bean Validation，失败 400/专门业务码）
  ├─ ② 邮箱唯一性校验（现状逻辑，返回 1001）
  ├─ ③ captchaService.verify(REGISTER, email, captcha)   ← 新增，必须通过
  ├─ ④ BCrypt 加密 → 落库（现状逻辑）
  └─ ⑤ 不签发令牌（维持「注册后手动登录」语义）
```

- **顺序说明**：先校验验证码再落库？或先查邮箱唯一再校验验证码？规划为：①密码一致性 → ②验证码校验 → ③邮箱唯一性 → ④落库（把「用户提交内容校验」尽量前置，验证码与唯一性顺序可在实现时调整，不影响语义）。

### 4.3 忘记密码（新增 `POST /auth/forgot-password`）

- **请求体**（规划 `ForgotPasswordRequest`）：`{email, captcha, newPassword, confirmPassword}`。
- **流程**：

```
forgotPassword(request)
  ├─ ① newPassword == confirmPassword 校验
  ├─ ② captchaService.verify(FORGOT_PASSWORD, email, captcha)  ← 必须通过
  ├─ ③ 反查 email → userId（getByEmail，@TableLogic 过滤已删用户）
  ├─ ④ BCrypt 加密 → updatePassword(userId, encoded)
  └─ ⑤ authSessionService.remove(userId)   ← 销毁全部会话（D5 统一语义）
```

- **不自动登录**（D3）：响应成功即止，前端引导携带新密码重新登录。
- **防枚举**：若邮箱未注册，步骤②/③ 之前就返回与「验证码已发送」**相同的成功文案/业务码**（见 §5），不暴露邮箱是否注册。

### 4.4 修改密码扩展（`POST /auth/change-password`）

- **请求体**（规划 `ChangePasswordRequest` 扩展）：`{oldPassword?, captcha?, newPassword, confirmPassword}`，双通道**二选一**（两者均传 → 400 冲突；均不传 → 400）。

| 通道 | 校验条件 | 说明 |
| :--- | :--- | :--- |
| A（现状） | `oldPassword` BCrypt 匹配当前用户密码 | 失败 1006 原密码错误 |
| B（新增） | `captchaService.verify(CHANGE_PASSWORD, 当前用户邮箱, captcha)` | 需要先给本人邮箱发送验证码（CHANGE_PASSWORD 场景发送要求登录且邮箱=本人） |

- **流程**：

```
changePassword(request)                  // 需登录，SecurityUtils.getCurrentUser()
  ├─ ① 双通道二选一校验（A 或 B 通过其一）
  ├─ ② BCrypt 加密 → updatePassword(id, encoded)  落库成功后再做 ③
  ├─ ③ authSessionService.remove(id)     ← 统一销毁会话（D5），失败 ERROR 告警不阻断
  └─ ④ 返回成功；前端引导重新登录（当前令牌已失效）
```

- **与现状的一致性**：通道 A 的销毁行为与现有实现完全一致，本方案不改变；通道 B 对齐到同一语义。
- **安全边界说明**：通道 B 本质是「邮箱可达 = 凭据可改」，邮箱一旦失守即密码失守——在文档与接口说明中明示该边界，并用「改密后统一销毁会话」做止损。

## 5. 防枚举与统一响应约定（安全）

| 关注点 | 处理 |
| :--- | :--- |
| 忘记密码场景邮箱枚举 | `FORGOT_PASSWORD` 发送时，对「邮箱未注册」与「验证码已发送」返回**完全一致的响应**（同 HTTP 状态 + 同业务码 + 同文案，如「若该邮箱已注册，验证码将发送至邮箱」） |
| 验证码校验失败 | 统一业务码，不区分「过期/不存在/错误」，避免泄露状态细节（与 refresh 统一 1019 的风格一致） |
| 跨场景复用 | key 绑定 `{scene}:{email}`，`verify` 必须显式传 scene |
| 重放 | 校验成功立即 DEL（用后即焚）；attempt ≥5 作废 |

建议沿用业务码段新增（以下编号为**规划值，实施时可调整**，不构成契约）：

| 规划编号 | 含义 |

| 1030 | 验证码发送过于频繁 |
| 1031 | 验证码无效或已过期 |
| 1032 | 验证码错误次数超限，请重新获取 |
| 1033 | 邮箱未注册（忘记密码场景统一文案，实际响应与成功一致） |

| 1035 | 改密必须提供旧密码或验证码之一（二选一校验失败） |

- 校验：成功且用后即焚（Re-display 后校验应失败）、错 5 次作废、过期失效、跨场景复用被拒（REGISTER 码不能过 FORGOT 校验）；
- 场景前置条件：注册发码要求邮箱未注册、忘记密码发码不允许未注册邮箱（响应一致性断言）、改密发码要求登录且邮箱=本人；
- 流程用例：忘记密码重置成功 → 旧 AT/RT 401 + Redis `qsx:auth:*` 键消失（机制层断言）；改密通道 B 成功 → 会话销毁断言（与通道 A 行为一致）；
- 失败矩阵：验证码缺失/错误/过期/超限、密码两次不一致、双通道都传/都不传。

> **机制层断言要求**（沿用项目测试红线）：验证「吊销即时生效」必须断言 Redis 键已消失，而非仅断言 401。
