# 05 · 业务功能与保护矩阵

本文按模块讲清「每个接口做什么、有哪些拦截、动了什么会话/缓存」，最后集中列出**已知缺口**。

## 1. 用户管理（8 个接口，需 `user:*` 权限）

| 接口 | 权限 | 关键行为 |
| :--- | :--- | :--- |
| `GET /api/users` | `user:page` | 按 email / nickname / status 筛选；分页上限 500（MyBatis-Plus `maxLimit`） |
| `GET /api/users/{id}` | `user:get` | 单条详情（不含密码） |
| `POST /api/users` | `user:create` | 邮箱唯一性校验；管理员建号**不**需要验证码 |
| `PUT /api/users/{id}` | `user:update` | 改名 / 改邮箱（唯一性，排除自己）/ 改状态 |
| `DELETE /api/users/{id}` | `user:delete` | 逻辑删除 + 释放邮箱 + 清会话 |
| `PUT /api/users/{id}/roles` | `user:assign-role` | 整表替换用户角色 |
| `POST /api/users/{id}/kick` | `user:kick` | 清目标会话（账号状态不变） |
| `GET/POST /api/users/import*`、`GET /api/users/export` | `user:import` / `user:export` | 见 §6 |

### 1.1 状态谓词：全链路「非 0 即禁用」

| 位置 | 判定 |
| :--- | :--- |
| `SecurityUser.isEnabled()` | `status == 0` 才放行 |
| `UserServiceImpl.isDisabling()` | `status != 0` 即禁用 |
| `AuthServiceImpl.refresh` 的查库兜底 | `status != 0` 即拒绝续期 |
| DTO 校验 | `@Min(0) @Max(1)` 限制取值（纵深防御） |

**四处必须用同一个谓词**。曾经的缺陷是：保护规则按 `status == 1` 判定、而账号生效逻辑按
`status != 0` 判定，于是传 `status=2` 就能绕过禁用保护（禁用超管、禁用自己）且不清理会话。

### 1.2 禁用即踢下线

`update` 传入非 0 状态时同步清理该用户会话三键 → 旧 AT 立即失效。
失败只告警不阻断：属性和「每请求查库的 `isEnabled()`」是第二道防线。
**解冻（0）不触发清理**，所以不存在「解冻后旧令牌复活」（旧令牌在禁用时就已删除）。

### 1.3 删除用户

```
① 不允许删自己 → 1022
② 内置超管不可删 → 1025
③ 释放邮箱：email 改写为 email + "#deleted_<时间戳>"
④ 逻辑删除（deleted=1）
⑤ 事务提交后：清会话三键 + 失效该用户权限缓存
```

第 ③ 步是「逻辑删除」与「邮箱唯一索引」的冲突解法：不改写邮箱的话，同一邮箱永远无法重新注册
（唯一索引不含 `deleted` 列）。已删除记录仍可追溯（原邮箱是改写值的前缀）。

> 会话清理放在**事务提交后**（`TransactionSynchronizationManager.registerSynchronization`）：
> 若在事务内执行，回滚会留下「用户其实没被删掉，会话却已被清空」的不一致。
> 权限缓存失效走 `AFTER_COMMIT` 事件，两者时机一致。

### 1.4 分配角色（整表替换）

先物理删旧关联，再批量插新（`insertBatch`），最后提交后失效该用户缓存。
`roleIds` 里的角色必须先校验存在（否则 1009）。

## 2. 角色管理（7 个接口，需 `role:*` 权限）

| 接口 | 权限 | 关键行为 |
| :--- | :--- | :--- |
| `GET /api/roles` | `role:page` | code / name / status 筛选 |
| `GET /api/roles/all` | `role:page` | **仅启用角色**（下拉用） |
| `GET /api/roles/{id}` | `role:get` | 详情 + 已绑定权限 ID 列表 |
| `POST /api/roles` | `role:create` | **编码判重包含逻辑删除行**（`countByCodeIncludeDeleted`） |
| `PUT /api/roles/{id}` | `role:update` | 改名/描述/状态；编码不可改（1024）；ADMIN 不可停用（1026） |
| `DELETE /api/roles/{id}` | `role:delete` | ADMIN 不可删（1011）；**删普通角色会级联解除用户与权限关联** |
| `PUT /api/roles/{id}/permissions` | `role:assign` | 整表替换角色权限 |

`update` 与 `delete` / `assignPermissions` 都在**改动关联表之前**反查受影响用户
（`selectUserIdsByRoleId`），提交后再失效其缓存——顺序原因见 [03-授权与RBAC.md](03-授权与RBAC.md) §3。

## 3. 权限管理（3 个接口，只读）

`GET /api/permissions`（`perm:page`）、`/all`（`perm:page`）、`/{id}`（`perm:get`）。

**权限码的维护走 `sql/init.sql`，不提供写接口**——权限码是鉴权键，改动风险高且频率极低，
把它做成接口只会增加误操作面。新增权限码同步三处的要求见 [03](03-授权与RBAC.md) §2。

## 4. 菜单管理（5 个接口）

| 接口 | 权限 | 关键行为 |
| :--- | :--- | :--- |
| `GET /api/menus/tree` | `menu:tree` | 全量菜单 + 按钮权限树（管理端） |
| `GET /api/menus/current` | 登录即可 | 当前用户菜单树（按权限过滤 + 补祖先链） |
| `POST /api/menus` | `menu:create` | 标识唯一（含已删行 1016）；父节点必须是 MENU（1015） |
| `PUT /api/menus/{id}` | `menu:update` | 标识不可改（1023）；**防环**（父节点不能是自身或子孙） |
| `DELETE /api/menus/{id}` | `menu:delete` | 有子节点禁删（1014）；先清角色-权限关联再逻辑删除 |

`update` / `delete` 同样在改动前反查持有该菜单/权限的用户并失效其缓存。

## 5. 操作日志（3 个接口，需 `log:*` 权限）

| 接口 | 权限 | 说明 |
| :--- | :--- | :--- |
| `GET /api/logs` | `log:page` | username / url / success / method / 时间段筛选 |
| `DELETE /api/logs/{id}` | `log:delete` | 物理删除单条 |
| `DELETE /api/logs` | `log:delete` | 物理清空全部 |

写入侧见 [06-基础设施、审计与测试.md](06-基础设施、审计与测试.md) §3。当前实现与注释里

## 6. Excel 批量导入导出

| 接口 | 权限 | 说明 |
| :--- | :--- | :--- |
| `GET /api/users/import/template` | `user:import` | 下载模板（邮箱 / 昵称 / 状态 / 角色编码） |
| `POST /api/users/import` | `user:import` | multipart 上传，单次 ≤ 1000 行 |
| `GET /api/users/export` | `user:export` | 按筛选条件全量导出，单次 ≤ 50000 行 |

设计要点：

- **文件不落盘**：导入用 SAX 流式读输入流，导出/模板直接写响应流。
- **整批校验 + 整体拒绝**：任一行不合法则**一行都不落库**，返回全部错误行明细（含 Excel 行号；
  行号 = `rowIndex + 1`，历史上曾因偏移一位排查半天）。
- **一次查库**：先收集全部邮箱与角色编码，一次查已存在邮箱、一次查角色映射，避免 N+1。
- **默认口令**：`import.default-password`（默认 `qsx123456`），**全部导入行复用同一个 BCrypt 哈希**
  （大批量导入的性能考虑）。
- 失败信息里会带 `e.getMessage()`（解析异常），便于排查但也泄露实现细节，见 §7。

## 7. 已知缺口（本地开发阶段有意搁置）

> 以下问题**均已核实**，在当前阶段（个人学习 / 本地开发）不影响使用，故未修复。
> 若本项目要作为生产基座，这张表应作为待办清单。

| # | 缺口 | 位置 | 影响 |
| :--- | :--- | :--- | :--- |
| 1 | **删除权限行无保护** | `PermissionServiceImpl.delete` | ADMIN 持有 `menu:delete`，误删系统权限码所在行（如 `role:update`）后，该接口对**所有人永久 403**：`uk_perm_code` 是物理唯一索引 + 判重含已删行 ⇒ 同 code 无法通过接口重建，只能改库。这与项目为 ADMIN 角色加 1026/1011 想避免的失控是同一类，但权限侧没有对称保护 |
| 2 | **审计日志可被一键抹除且不留痕** | `OperationLogServiceImpl.clear` + `OperationLogAspect` 排除 `/api/logs` | 持有 `log:delete` 者可整体销毁审计数据，且删除动作本身不进审计表 |
| 3 | **未认证请求可无限写审计表** | `RestAuthenticationEntryPoint` | 只对「Redis 基础设施异常」豁免落库；伪造 token 的 401 一律落库（实测：匿名 30 次请求 = 30 行）。无保留策略，表会持续膨胀 |
| 4 | **两条自助提权路径无护栏** | `UserServiceImpl.assignRoles` / `UserImportExportServiceImpl` | ① 持有 `user:assign-role` 者可给自己绑 `ADMIN`；② `user:import` 可导入角色为 `ADMIN` 的新账号（密码是公开的默认口令）。同时 `assignRoles` 是唯一**零保护**的生命周期入口：可把内置超管的 ADMIN 角色整表清空（架空超管） |
| 5 | **Excel 导出公式注入** | `exportUsers` 原样写出 `nickname` | 昵称仅 `@Size(max=50)` 校验，任何访客可注册 `=HYPERLINK(...)` 形式的昵称；管理员导出后用 Excel 打开即触发（CWE-1236）。修法：导出前对 `= + - @` 开头的单元格加单引号前缀 |
| 6 | **默认凭据** | `application.yml` / `init.sql` | SQL 明文打印（`log-impl: StdOutImpl`）+ `com.qsx: debug`；预置超管 `admin123`；导入默认口令 `qsx123456` 且**不强制首次改密** |
| 7 | **CORS 通配** | `SecurityConfig.corsConfigurationSource` | `allowedOriginPatterns("*")` + `allowCredentials(true)` |
| 8 | **系统异常对 HTTP 层隐藏** | `GlobalExceptionHandler.handleException` | 无 `@ResponseStatus` ⇒ 真 500 以 HTTP 200 返回，LB/监控看不到 5xx，无法告警 |
| 9 | **登录无失败限制 / 可枚举邮箱** | `AuthServiceImpl.login` + `register` 的 1001 | 无锁定、无延时递增；配合注册接口的 1001 可批量探测哪些邮箱已注册 |
| 10 | **删除用户残留关联行** | `UserServiceImpl.delete` | 只逻辑删除用户，不清理 `sys_user_role`（孤儿行；重新注册是新 userId，不会继承角色） |

## 8. 保护矩阵（完整版）

| 码 | 含义 | 触发点 |
| :--- | :--- | :--- |
| 1011 | 内置超管角色不可删除 | `DELETE /api/roles/{id}` |
| 1020 | 内置超管用户不可禁用 | `PUT /api/users/{id}`（status≠0） |
| 1021 | 内置超管用户不可强制登出 | `POST /api/users/{id}/kick` |
| 1022 | 不允许对自己执行该操作 | 禁用自己 / 删除自己 / 踢自己 |
| 1023 | 菜单或权限标识创建后不可修改 | `PUT /api/menus/{id}` |
| 1024 | 角色编码创建后不可修改 | `PUT /api/roles/{id}` |
| 1025 | 内置超管用户不可删除 | `DELETE /api/users/{id}` |
| 1026 | 内置超管角色不可停用 | `PUT /api/roles/{id}`（status≠0） |

**身份判定统一走 `UserMapper.existsRoleCode`（不过滤角色状态）**，原因见 [03](03-授权与RBAC.md) §5。

> 注意矩阵的**不对称**：禁用/踢人/删除都有超管保护，但 `assignRoles`（§7 第 4 条）没有任何保护；
> 角色侧有「内置角色不可删/不可停用」，权限侧（§7 第 1 条）则什么都没有。
