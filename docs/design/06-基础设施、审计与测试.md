# 06 · 基础设施、审计与测试

## 1. 统一返回与错误码约定

所有接口返回 `Result{code, message, data}`，分页接口的 `data` 是 `PageResult`。

| 场景 | HTTP 状态 | body `code` |
| :--- | :--- | :--- |
| 成功 | 200 | 200 |
| **业务异常** | **200** | 业务码（1001~1032 等） |
| 参数校验失败 | 200 | 400 |
| 请求体无法解析（JSON 语法错 / 枚举取值非法） | 200 | 400 |
| 未登录 / 令牌失效（URL 级鉴权） | **401** | 401 |
| 已登录但无权限 | **403** | 403 |
| 未预期的系统异常 | 200 | 500 |

> **断言一律看 body 里的 `code`，不要看 HTTP 状态**——这是本项目最容易写错断言的地方，
> 测试里 `andExpect(isOk())` 拦不住任何业务失败。

错误码分段：

| 段 | 含义 |
| :--- | :--- |
| 200 / 400 / 401 / 403 / 500 | 通用 |
| 1001~1008 | 认证与用户（邮箱已注册 1001、邮箱或密码错误 1002、账号禁用 1003、原密码错误 1006…） |
| 1009~1012 | 角色与权限 |
| 1013~1016 | 菜单（存在子菜单 1014、父菜单无效 1015、标识已存在 1016） |
| 1017~1018 | Excel 导入（校验失败 1017、超量 1018） |
| 1019~1026 | 会话与保护（刷新令牌无效 1019、超管保护 1020/1021/1025/1026、不可操作自己 1022、标识不可改 1023/1024） |
| 1027~1032 | 邮箱验证码（发送过于频繁 1027、验证码无效 1028、错误超限 1029、两次密码不一致 1030、改密需二选一 1031、仅限本人邮箱 1032） |

完整清单与文案见 `qsx-common` 的 `ResultCode`。

## 2. 全局异常处理（`qsx-framework`）

| 处理器 | 返回 | 备注 |
| :--- | :--- | :--- |
| `BusinessException` | HTTP 200 + `e.getCode()` | 业务失败的统一出口 |
| `MethodArgumentNotValidException` | HTTP 200 + 400 | 取第一个字段错误的消息；**补记一条 400 审计**（参数校验发生在切面之前，切面看不到） |
| `HttpMessageNotReadableException` | HTTP 200 + 400 | JSON 解析失败 / 枚举取值非法。**不加这个处理器会落到兜底的 500**——把「客户端传错参数」报成系统故障 |
| `AccessDeniedException` | **HTTP 403** + 403 | `@PreAuthorize` 拒权的出口 |
| `Exception`（兜底） | HTTP 200 + 500「系统繁忙，请稍后重试」 | 不泄露堆栈；但见 [05](05-业务功能与保护矩阵.md) §7 第 8 条（监控看不到 5xx） |

## 3. 操作日志（审计）

### 3.1 写入链路

```
OperationLogAspect（@Around 包级切点 com.qsx.web.controller..*.*(..)）
  ├─ 业务语义判定：Result.code == 200 才算成功
  ├─ 记录 操作人 / 方法 / URL / httpStatus / success / errorMsg / costMs
  └─ finally：accessLogRecorder.record(command)   ← 端口（qsx-common 定义）
        → OperationLogServiceImpl.record()  @Async("operationLogExecutor")  ← 业务模块实现
```

**切面靠包路径定位**：`com.qsx.web.controller` 是契约，新增控制器沿用该包即自动纳入审计。

### 3.2 三处补记（切面覆盖不到的场景）

| 场景 | 谁补记 | 原因 |
| :--- | :--- | :--- |
| 401 未登录 | `RestAuthenticationEntryPoint` | 请求在进入 Controller 前就被拦下 |
| 403（URL 级规则） | `RestAccessDeniedHandler` | `anyRequest().authenticated()` 触发的拒绝 |
| 403（`@PreAuthorize`） | `OperationLogAspect` | 方法级拒权在切面内抛出、被 `catch (AccessDeniedException)` 捕获 |
| 400 参数校验 | `GlobalExceptionHandler` | 参数解析发生在切面 `proceed()` 之前 |

**例外：`/api/logs` 前缀被切面整体跳过**（避免「日志的日志」无限膨胀）；
代价是日志的查询与删除都不进审计表——见 [05](05-业务功能与保护矩阵.md) §7 第 2 条。

### 3.3 两个降噪/兜底约定

- **Redis 故障时不写 401 审计**：认证链路因基础设施异常判未认证时会打标记
  （`SecurityConstants.AUTH_INFRA_ERROR_ATTR`），401 处理器见到标记只打 WARN、不落库——
  否则故障期 100% 请求都 401，队列打满后转同步写库，会把 Redis 局部故障放大成全站不可用。
- **`@Async` 不得自调用**：`OperationLogServiceImpl.record()` 的异步靠 Spring 代理生效，
  改成同类内部调用会**静默失效**（日志退化为同步落库，主请求被 DB 写入阻塞，且没有编译错误）。

## 4. 异步线程池（`qsx-framework/AsyncConfig`）

| Bean | 用途 | 参数 |
| :--- | :--- | :--- |
| `operationLogExecutor` | 审计落库 | core 2 / max 8 / queue 1000 / `CallerRunsPolicy`（日志不能丢） |
| `captchaMailExecutor` | 验证码邮件投递 | core 2 / max 4 / queue 16 / `CallerRunsPolicy`（验证码不能丢，见 [04](04-邮箱验证码.md) §4） |

两个池分开的原因：邮件受外部 SMTP 影响、耗时不可控，与数据库写入混用会互相拖累。

## 5. 持久层配置（`MybatisPlusConfig`）

- 分页插件 `PaginationInnerInterceptor`，**`setMaxLimit(500)`**：任何 `pageSize` 超过 500 会被截断，
  避免一次查询把整表拉进内存。
- 自动填充：`createTime` / `updateTime`（`strictInsertFill` / `strictUpdateFill`）。
- 逻辑删除：全局 `logic-delete-field: deleted`，`deleted=1` 表示已删；
  它带来的两个连带影响（唯一索引冲突、判重必须含已删行）见 [03](03-授权与RBAC.md) §6。

## 6. 测试体系

### 6.1 双轨制

| 轨 | 形式 | 覆盖 |
| :--- | :--- | :--- |
| **Track A** 自动化集成测试 | `@SpringBootTest` + MockMvc + **真实本地 MySQL/Redis** | 204 例 / 23 个测试类 |
| **Track B** 真实 HTTP | 起 fat jar 逐接口真实调用，记录请求与完整响应 | 230 条有效明细（R1~R6） |
| **机制层断言** | 直查 Redis / SQL | 会话三键形态与 TTL、权限缓存键失效、验证码键的消耗与作废 |

结果与逐笔明细见 [`docs/test/项目测试报告.md`](../test/项目测试报告.md)（§九 验证码轮次、§十 注册/登录/验证码专项轮次），
原始请求/响应见同目录 `项目测试报告.json`。

### 6.2 `BaseIntegrationTest` 提供的能力

| 成员 | 说明 |
| :--- | :--- |
| `register(email, password)` | **内部走真实发码链路**：调 `/auth/captcha` → 从 Redis 取码 → 带码注册。因此各测试类的调用点无需关心验证码 |
| `loginGetToken` / `loginGetAuth` | 登录取 AT，或取完整会话（`token` / `refreshToken` / `userId` / `email`） |
| `adminToken()` | **走真实 `assignRoles` 链路**构造一个超管，而不是直接改库 |
| `postJson` / `bearerHeader` / `uniqueEmail` | 通用工具 |
| `userMapper` / `roleMapper` / `jdbcTemplate` / `stringRedisTemplate` | 直查数据库与 Redis（机制层断言用） |

### 6.3 清理范围（**红线**）

用例前后各清一次，范围**显式限定**：

| 对象 | 范围 |
| :--- | :--- |
| 用户 | 只删 `email LIKE '%@test.com%'`（含被逻辑删除后改写成 `...#deleted_<ts>` 的行） |
| 角色 | 只删 `code LIKE 'test-%'`（含逻辑删除行）+ 两侧关联 |
| 操作日志 | 全表清空（非预置数据） |
| Redis | 按**显式前缀清单** SCAN 删除：`qsx:auth:perm:` / `qsx:auth:at:` / `qsx:auth:rt:` / `qsx:auth:session:` / `qsx:auth:cap:` |

**为什么不能图省事**：

- `DELETE FROM sys_user` 会连预置超管一起删掉（早期实现就是这样，导致「跑一次测试就要手工恢复
  一次 admin」反复发生）；
- `userMapper.delete(null)` 更危险——带 `@TableLogic` 的实体会变成**全表逻辑删除**；
- Redis 清理是**显式前缀枚举而非 `qsx:auth:*` 通配**：新增一类键必须登记，
  否则会跨用例残留（验证码的限流与错次计数残留就会让相关用例随机转红）。

> **测试直接复用本地开发库与开发 Redis**（没有独立测试库），所以：**不要在本地应用正服务
> 会话时跑测试**——会清掉在线会话的 Redis 键。

### 6.4 断言纪律

- **断言打到机制层**：验证「吊销即时生效」，除了断言 401 还要断言 Redis 键已消失——
  否则每请求查库的 `isEnabled()` 兜底会让**漏实现**的代码也通过测试。
- **失败用业务码，不用 HTTP 状态**（见 §1）。
- **修复类改动要验证「回退后确实转红」**：`AdminProtectionTest` 曾在提交前把生产改动 stash 掉
  重跑，确认用例从绿转红且失败信息为「expected 1020 but was 200」——避免写出恒绿的假回归。
- **概率性的断言不要写**：例如「新旧验证码必然不同」有 1e-6 的偶然概率，
  改成断言机制本身（重发后错误计数被清零）。

### 6.5 端到端冒烟

`CaptchaMailSmokeTest` 覆盖「`@Async` 投递 → 真实 SMTP → Mailpit 收信 → 正文含码」这条链路，
是唯一会碰真实发信过程的用例；**Mailpit 未启动时用 `assumeTrue` 整类跳过**（本地设施缺席不应
把基线染红，但见到 SKIPPED 要意识到这条链路没被验证）。

> 环境事实备查：Mailpit 取单封邮件的路径是 **`/api/v1/message/{ID}`（单数）**；
> 复数路径返回 404 与纯文本 `File not found`，不是 JSON。
