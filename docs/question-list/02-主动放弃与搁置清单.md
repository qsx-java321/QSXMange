## 二、设计取舍（明确不修，避免误当 bug 修）

| 取舍 | 说明 | 边界 |
| :--- | :--- | :--- |
| 会话层 fail-closed | Redis 故障 = 拒绝认证（宁可不放行）；权限缓存层才 fail-open（降级查库）。**两边界不可混淆** | 部署须配 Redis 监控告警（见 #12）；另注意 #25/#30 两处 fail 语义的实现缺陷 |
| 会话/验证码脚本仅支持单节点 Redis | 键无 hash tag，上集群会 CROSSSLOT；Redis 禁 `allkeys-lru` 淘汰（会话键被淘汰 = AT 无法吊销） | 生产若上集群需重写脚本（大改，别轻易动）——**补正见 §四.2** |
| 登录失败不区分账号/密码错误业务码 | 统一 1002，配合 Spring Security 的 dummy bcrypt 比对，防邮箱枚举——**计时侧信道已实测排除**（见 05 §三） | 登录失败限流与 CPU 放大仍待办（#18） |
| FORGOT_PASSWORD 对未注册邮箱静默跳过 | 防枚举、防垃圾邮件滥用 | 已实测响应一致；但**发码间隔键的有无**仍构成旁路信道（未注册=不占限流键 ⇒ 二次调用返回码不同），若要彻底防枚举需补"未注册也占限流键" |
| 管理员建号与后台导入不走验证码 | 身份由 `user:create`/`user:import` 鉴权保障 | **已收口**（2026-09-29）：两条路径落库的账号都置 `must_change_password=1`，首次登录即强制改密（1037）；**另注意导入的昵称默认取邮箱 ⇒ #19** |
| 分布式会话/权限缓存不做本地二级缓存 | 单实例部署下无收益，且引入一致性成本 | 若将来多实例，需重新评估 #40（雪崩/击穿）与进程内缓存的取舍 |
| 业务异常统一 HTTP 200 + body 业务码 | 前端契约简单、与既有测试口径一致 | 代价见 #10（监控看不到 5xx）与 #28（部分异常连审计都没有） |

## 三、工程约束（非缺陷，但决定修复方式）

| 约束 | 影响 |
| :--- | :--- |
| 测试基座 `adminToken()` 走 service 直调 `assignRoles` 自绑 ADMIN | 修复 #1 时若加"授予 ADMIN 需超管身份"（闸 2）会破坏该链路 ⇒ 闸 2 排期后置，需同步迁移测试底座 |
| 业务异常统一 HTTP 200 + body 业务码 | 修复 #10 时**只对兜底 500** 加 `@ResponseStatus`，不能影响既有业务契约 |
| 权限缓存失效必须在改动关联表**之前**反查受影响用户 | 新增任何写权限/角色的逻辑都要遵守，否则缓存留脏至 TTL |
| `@Async` 不得自调用 | 新增异步逻辑（如审计限频 #9、投递重试 #15）需走外部 Bean 代理 |
| **库 collation 是 `utf8mb4_general_ci`（大小写不敏感）** | 任何"邮箱按原样比较 / 按原样构造键"的推理都不成立——#20 就是这么来的；新增任何以邮箱为键或为判据的逻辑，必须显式定义大小写口径 |
| **本地 Mailpit 是毫秒级本地响应** | 邮件链路的故障放大行为（#22）在本机**不可验证**，只能靠代码审查 + 生产形态观测；涉及投递的改动不要以"本地正常"作为验证结论 |
| `MyBatis-Plus` 的 `insertBatch` 是单条多值 INSERT | 批量大小需受控（当前 1000 行上限在业务层，但见 #31：上限判定时机在后） |
| 「断言要打到机制层」 | 验证"吊销即时生效""缓存已失效"这类能力时，除断言响应码外必须直查 Redis/DB——否则每请求查库的兜底会让漏实现的代码也通过测试 |

## 四、反悔记录（被推翻的搁置理由 / 结论）

### 4.1 `CaptchaRedisKeys.normalizeEmail` 的注释理由错误 ⇒ 产出 #20
原注释（当前源码仍在）："邮箱在库中是按原样存储与比较的，此处不引入大小写折叠，避免出现「验证码键用小写、库查询用原样」的第二套规则。"
**该前提不成立**：库是 `utf8mb4_general_ci`，`SELECT 'a@x.com' = 'A@X.COM'` 实测返回 1。所谓"按原样比较"本就是错的，反而是注释自己在制造第二套规则。修复见 03（#20），修完请一并改写该注释。

### 4.2 「上集群补 hash tag 即可」的隐含结论不充分
`CLAUDE.md` 与设计 02 §8 记的是"无 hash tag ⇒ CROSSSLOT"。但**补 hash tag 不足以完成迁移**：
- 脚本内要删的旧 at/rt 键名由 `ARGV` 前缀 + **进脚本后才知道的旧令牌值**拼出，这些键**从未出现在 `KEYS[]`**，Redis 集群会对"访问未声明键"直接报错；
- AT 的键名由客户端令牌决定，天然散布所有 slot。
⇒ 真要上集群，需把键结构改成 `at:{userId}:{token}` 这类**以用户为 hash tag** 的形态，并在协议层带上 userId（客户端契约变更）。当前结论仍是"不迁移"。

### 4.3 「绝对上限 30 天」对存储中的凭据并不成立（文档口径需修正）
`max-lifetime: 30d` 的判定点在 `auth_session_rotate.lua` 的**轮换路径内**；会话键 TTL 每次轮换都 `EXPIRE` 续 `rt-ttl`（7d）。因此一个自 29 天起就不再刷新的会话，其 session/rt 键最长可存在约 36–37 天。
这**不构成越权**（任何一次 refresh 都会在脚本里被判 `EXPIRED`），但与"绝对上限 30 天"的字面承诺不符，排查时容易误判。要么在文档里写明"绝对上限在刷新时判定"，要么给 session 键额外设一个不超过剩余上限的 TTL。

### 4.4 「导出公式注入」被撤销（原 P0）
原文（`03-修复方案` 与 `docs/design/05` §7 第 5 条）称 "POI 对 `=` 开头字符串自动推断为公式类型"。实测 EasyExcel 4.0.3 + POI 5.2.5 写出的是 `t="inlineStr"`（无 `<f>`），POI 读回类型为 `STRING`。**结论与修法一并撤销**（原修法会给 `-`/`+`/`@` 开头的正常昵称加可见撇号）。详见 05 §二。
