## #21 内置超管角色的**权限绑定**保护（P0 新增，与 #2 对称）

### 审查结论（源码已核实）

- [RoleServiceImpl.assignPermissions](file:///d:/Java_SE/GitProject/QSXManager/qsx-module-system/src/main/java/com/qsx/service/impl/RoleServiceImpl.java#L164-199) 只做"角色存在 / 权限存在"校验，**对内置 ADMIN 角色零保护**；同文件的 `update`（1026）、`delete`（1011）**都写了同一句理由**："防止没人能再通过接口把权限启用回来"。
- `AssignPermissionsRequest` 允许 `permissionIds` 为 null/空数组，语义即"清空全部"。

比 #2 更隐蔽之处：不需要"删除"这种明显危险的动作，管理端「编辑 ADMIN 角色、只勾选当前页权限后保存」就会触发。

## #19 邮箱长度：一处约束解决「注册 500」与「不可删账号」

### 审查结论（源码已核实 + 实测）

- email 只有 `@Email` 而**不限制总长度**（实测 Hibernate Validator 接受 260 字符），列是 `VARCHAR(128)`；`nickname` 是 `VARCHAR(50)`，而**昵称留空时默认取邮箱**（三处：`AuthServiceImpl.register`、`UserServiceImpl.create`、`UserImportExportServiceImpl.importUsers`）。
- `UserServiceImpl.delete` 用 `email + "#deleted_" + 13 位毫秒`（固定 22 字符）释放唯一索引 ⇒ **邮箱 ≥ 107 字符的用户永远删不掉**。
- 实测三连（见 05 §一）：60 字符邮箱+空昵称 → 500；132 字符邮箱 → 500；117 字符邮箱用户 DELETE → 500 且行仍在。

### 方案 A（推荐）：约束邮箱上限 = 110，并截断昵称兜底

| 文件 | 改动 |
| :--- | :--- |
| `.../dto/request/RegisterRequest.java`、`UserCreateRequest.java`、`UserUpdateRequest.java` | email 加 `@Size(max = 110, message = "邮箱长度不能超过110")` |
| `.../dto/request/CaptchaSendRequest.java`、`ForgotPasswordRequest.java` | 同上（保证「发码能发、注册被拒」不会错位） |
| `AuthServiceImpl.register` / `UserServiceImpl.create` / `UserImportExportServiceImpl.importUsers` | 昵称兜底改为截断：`email.length() > 50 ? email.substring(0, 50) : email` |
| `UserImportExportServiceImpl.validateRow` | 邮箱长度校验加一行：`email.length() > 110` → 该行报错（走 1017 整批拒绝 + 行号） |

```java
/** 昵称缺省值：取邮箱，但必须截断到 nickname 列宽（VARCHAR(50)）。
 *  历史上直接写整串邮箱，邮箱 > 50 字符时 INSERT 触发 1406，接口返回 500 而非参数错误。 */
private static String defaultNickname(String email) {
    return email.length() > NICKNAME_MAX ? email.substring(0, NICKNAME_MAX) : email;
}
```

- **为何取 110 而不是 128**：删除后缀固定 22 字符（`#deleted_` + 13 位毫秒），必须留余量；110 远大于真实地址的常见长度。
- **替代方案 B（不推荐，供比较）**：保留邮箱 128 上限，把删除时的后缀改成定长（如 `LEFT(email, 106) + '#' + id`）。它保留了更长的邮箱，但把"改写邮箱"的逻辑复杂化，且 `id` 位数变化仍要重新算边界——**方案 A 一处约束、三处受益，更符合项目"用一个谓词回答一个问题"的风格**。

## #20 验证码 Redis 键：统一大小写口径

### 审查结论（源码已核实 + 实测）

- `CaptchaRedisKeys.normalizeEmail` 只 `trim()`，其注释断言"邮箱在库中是按原样存储与比较的"——**该前提错误**：库 collation 是 `utf8mb4_general_ci`（实测 `SELECT 'a@x.com' = 'A@X.COM'` → 1）。
- 发码侧键用**客户端原样**输入、校验侧用 **`account.email()`（库中原样）** ⇒ 大小写不同即键不命中。实测：小写发码 → 改密 1028；原样发码 → 200。
- 登录本身大小写不敏感（实测小写可登录）⇒ 用户完全可能带着不同大小写进来。

### 修改清单

| 文件 | 改动 |
| :--- | :--- |
| `.../service/captcha/CaptchaRedisKeys.java` | `normalizeEmail` 改为 `trim().toLowerCase(Locale.ROOT)`，并**改写那条错误的注释**（说明库 collation 为 ci，故必须折叠） |

```java
/**
 * 邮箱归一化——发送与校验必须用同一口径。
 *
 * 折叠大小写是必须的：库列是 utf8mb4_general_ci，比较本来就大小写不敏感
 * （`'a@x.com' = 'A@X.COM'` 为真），登录因此也大小写不敏感；若验证码键保留原样大小写，
 * 用户以小写邮箱登录后再发码/校验就会算出两个不同的键，表现为「码刚发就说过期」（1028）。
 *
 * 反例记录：早期注释称「库中按原样存储与比较，故不折叠」——该前提不成立，已因此产生
 * 「大小写不一致时改密验证码通道永久失效」的缺陷。
 */
public static String normalizeEmail(String email) {
    return email == null ? null : email.trim().toLowerCase(Locale.ROOT);
}
```

- **单点修复**：`CaptchaServiceImpl.verify` 内部同样调用 `normalizeEmail`，因此发码/校验两侧自动一致，无需改调用方。
- **副作用评估**：Redis 中已存在的混合大小写键会变成孤儿（TTL 5 分钟 / 24 小时自然过期），无需迁移；`AuthServiceImpl.sendCaptcha` 的 `equalsIgnoreCase` 判定不受影响。
- `REGISTER` / `FORGOT_PASSWORD` 场景同样受益（客户端两次请求大小写不同时不再失败）。

### 测试计划（新增）

| 用例 | 断言 |
| :--- | :--- |
| 注册 `CaseTest@test.com` → 用**小写**登录成功 | 200（对照，证明库 ci） |
| 用小写邮箱发 `CHANGE_PASSWORD` 码 → 改密 | **200**（修复前为 1028） |
| 机制层 | 该用户的会话三键已清（改密统一销毁会话）、验证码键为小写形态 |
| 回归：发码/校验/忘记密码/注册全链路 | 全绿（CaptchaTest、ForgotPasswordTest、ChangePasswordChannelTest） |

@Data
@Validated
@Component

**撤销依据（实测，见 05 §二）**：文档原称 "POI 对 `=` 开头字符串自动推断为公式类型"。实测 EasyExcel 4.0.3 + POI 5.2.5 写出的是 `t="inlineStr"` 字符串单元格（XML 中无 `<f>` 元素），POI 读回类型为 `STRING` ⇒ Excel 打开不会执行。

**同时撤销其修复方案**：原「方案 A：对 `= + - @` 开头的字段加 `'` 前缀」会把 `-小明`、`+8613…` 这类**正常昵称**污染成可见撇号——**做了比不做更差**。

**保留的注意事项**：
- 若将来改为导出 CSV，公式注入会**立即成立**（CSV 无单元格类型，由 Excel 自行解释），届时应按 CWE-1236 处理；
- 若将来改用 `WriteCellData#setFormula` 或模板写值，也会重新引入该问题——**改导出实现前回读本节**。
