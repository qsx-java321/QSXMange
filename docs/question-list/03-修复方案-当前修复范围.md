### 闸 3（必做，防批量签发）——导入校验唯一一处

```java
// validateRow 内，拆 roleCodes 的循环：

    errors.add("第 " + row.getRowNum() + " 行：禁止将内置超管角色分配给导入用户");

- 复用"整批校验 + 整体拒绝"语义：错误自然走 `IMPORT_VALIDATE_FAILED`（1017），**无需新错误码**；返回含 Excel 行号。
- **无需操作者身份判断**：直接禁止导入任何 ADMIN 绑定（与闸 1"超管角色一经授予改库才能解除"的设定自洽——导入者不该拥有"先造超管再纠正"的摆布能力）。

### 闸 2（后置，防低权限者直接授予 ADMIN）——暂不实施的原因

- 语义：`roleIds` 含 ADMIN 且操作者（`SecurityUtils.getCurrentUserId()`）非内置超管 → 拒绝（拟新码 1034）。
- **破坏性**：`adminToken()` 当前是"自注册 → service 自绑 ADMIN"（[BaseIntegrationTest.java:326-333](file:///d:/Java_SE/Git/QSXManager/qsx-admin/src/test/java/com/qsx/BaseIntegrationTest.java#L326-333)），操作者当时不是超管 ⇒ 闸 2 会令全量依赖它的测试崩。需先迁移测试底座（改用预置超管经 HTTP 授权新用户）。
- 结论：**闸 1 + 闸 3 已封死最高危路径**（架空超管、批量签发）；残留面 = "管理员已把 `user:assign-role` 交给某人、此人再授 ADMIN"——属权限点设计问题，列入 04 待办。

## #2 权限删除保护：主闸"系统内置权限不可删"

### 审查结论（源码已核实）

- [PermissionServiceImpl.delete](file:///d:/Java_SE/Git/QSXManager/qsx-module-system/src/main/java/com/qsx/service/impl/PermissionServiceImpl.java#L156-176)：仅"有子节点禁删"；删除会物理清 `sys_role_permission` → 连坐 ADMIN；判重建撞唯一索引。

// PermissionConstants
public static final Set<String> BUILT_IN_CODES = Set.of(
        USER_PAGE, USER_GET, USER_CREATE, USER_UPDATE, USER_DELETE,
        USER_ASSIGN_ROLE, USER_IMPORT, USER_EXPORT, USER_KICK,
        ROLE_PAGE, ROLE_GET, ROLE_CREATE, ROLE_UPDATE, ROLE_DELETE, ROLE_ASSIGN_PERM,

public void delete(Long id) {
    Permission permission = getPermission(id);
    // 主闸：系统内置权限码不可删（与「内置角色不可删 1011/不可停用 1026」对称）
    if (PermissionConstants.BUILT_IN_CODES.contains(permission.getCode())) {
        throw new BusinessException(ResultCode.SYSTEM_PERMISSION_CANNOT_DELETE);
    }
    if (permissionMapper.selectCount(...parentId...) > 0) { throw 1014; } // 原有子节点检查
    // ……原有逻辑不动
}
```

### 设计决定与取舍

- **判 code 而非 id/type**：code 是鉴权键且与注解同源；id 不稳定；type 分不清"系统预置/自建"。
- **不做"被引用不可删"**：现有语义就是"级联解除关联再删"（文档化设计）；加引用保护会让删除自建菜单必须先逐个解绑，属过度设计。自建权限可换 code 重建，高危面（23 个预置码）已被主闸覆盖。

## #3 Excel 导出公式注入：出口净化

### 审查结论（源码已核实）

- [exportUsers](file:///d:/Java_SE/Git/QSXManager/qsx-module-system/src/main/java/com/qsx/service/impl/UserImportExportServiceImpl.java#L217-252) 原样写 `nickname`；[RegisterRequest](file:///d:/Java_SE/Git/QSXManager/qsx-module-system/src/main/java/com/qsx/web/dto/request/RegisterRequest.java#L32) 昵称仅 `@Size(max=50)`。
- 关键机制：POI（EasyExcel 底层）`setCellValue(String)` 对 `=` 开头字符串**自动推断为公式类型** → Excel 打开即执行。缓解思路二选一：
  - **A（推荐，一行/字段）**：危险前缀前加单引号 `'`（OWASP 标准做法）；代价是 Excel 打开时会**显示撇号**（显示略有瑕疵，功能安全）。
  - **B（显示干净，改造成本高）**：`WriteCellData<String>` + `setFormula(Boolean.FALSE)` 强制字符串类型，打开不显示撇号；需改导出模型或自定义 Converter。
- 结论：**本阶段采用方案 A**（改动最小、OWASP 认可）；将 B 列为后续显示优化项。

### 修改清单

| 文件 | 改动 |
| :--- | :--- |
| `qsx-module-system/.../service/impl/UserImportExportServiceImpl.java` | 新增 `escapeFormula` 并应用到导出行的字符串字段 |

### 核心代码

```java
/** 公式注入防护：以 = + - @ 或制表符/回车开头的单元格加单引号前缀（CWE-1236） */
private static String escapeFormula(String s) {
    if (s == null || s.isEmpty()) {
        return s;
    }
    char c = s.charAt(0);
    return (c == '=' || c == '+' || c == '-' || c == '@' || c == '\t' || c == '\r') ? "'" + s : s;
}

// exportUsers 组装行：对来源于库的字符串字段统一净化
row.setEmail(escapeFormula(user.getEmail()));
row.setNickname(escapeFormula(user.getNickname()));
row.setRoleCodes(escapeFormula(String.join(",", ...)));
// status("正常"/"禁用") 与 createTime 为程序生成常量，无需处理
```
