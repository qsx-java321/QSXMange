### 逐项明细（关键核实点）

#### #19 邮箱长度无上限（P1，实测）
- **位置**：`RegisterRequest`/`UserCreateRequest` 的 email 只有 `@Email`（**不限制总长度**，实测 Hibernate Validator 接受 260 字符）；`sys_user.email VARCHAR(128)`、`nickname VARCHAR(50)`（`sql/init.sql`）；昵称留空时默认取邮箱（`AuthServiceImpl.register` / `UserServiceImpl.create` / `UserImportExportServiceImpl.importUsers` **三处同一写法**）。
- **实测三连**：注册 60 字符邮箱 + 昵称留空 → 500；注册 132 字符邮箱 → 500；给 117 字符邮箱的用户执行 `DELETE /api/users/{id}` → **500 且行仍在**。
- **不可删的根因**：`UserServiceImpl.delete` 把邮箱改写成 `email + "#deleted_" + 13 位毫秒`（固定 22 字符后缀）⇒ **邮箱 ≥ 107 字符的用户永远无法删除**（`VARCHAR(128)` 溢出、MySQL 为 `STRICT_TRANS_TABLES`）。
- **后果**：注册是匿名接口 ⇒ 任何访客都能造出「管理员删不掉的账号」；三处都是 `HTTP 200 + body 500`（监控看不到）。
- **修法**：收敛邮箱上限。理论上界是 106（128 − 22），**实施取 100**（`UserConstants.EMAIL_MAX`，给后缀格式微调留余量）；
  原先方案写的是 110，那是错的（110 + 22 = 132 > 128，仍会 500），已在实施时改正。

#### #20 验证码键大小写口径（P1，实测）
- **位置**：`CaptchaRedisKeys.normalizeEmail` 只做 `trim()`，注释声称「邮箱在库中是按原样存储与比较的」——**该前提是错的**：库是 `utf8mb4_general_ci`，比较大小写不敏感（实测 `SELECT 'a@x.com' = 'A@X.COM'` → 1）。
- **实测**：同一用户、同一令牌，小写邮箱发码 → 改密返回 `1028`；原样邮箱发码 → `200` 成功。
- **机制**：发码侧键用**客户端原样**（`AuthServiceImpl.sendCaptcha` → `captchaService.send`），校验侧用 **`account.email()`（库中原样）**（`AuthServiceImpl.changePassword`）⇒ 两者不同 ⇒ 键不命中。
- **后果**：登录本身大小写不敏感 ⇒ 用户完全可能带着不同大小写进来，此时验证码改密通道**永远失败**，且报的是「验证码无效或已过期」，排查方向被带偏。
- **修法**：键构造与比较统一 `toLowerCase(Locale.ROOT)`，并改写那条注释。

#### #21 超管角色的权限绑定无保护（P0，读码）
- **位置**：`RoleServiceImpl.assignPermissions` 对内置 ADMIN 角色零保护；同文件的 `update`（1026 不可停用）、`delete`（1011 不可删除）**都明确写了理由**：「停用/删掉后没人能再把权限启用回来」。
- **危害**：`PUT /api/roles/{ADMIN}/permissions` 传 `{"permissionIds":[]}` ⇒ ADMIN 角色瞬间失去全部权限，**连恢复用的 `role:assign` 也一起没了**；角色仍是启用状态、code 不可改、角色不可删不可停 ⇒ 只能改库。
- **比 #2 更隐蔽**：在管理端「编辑 ADMIN 角色、只勾选当前页权限」这类常规操作即可触发；与 #2 是同一类失控，文档此前只记了权限侧。

#### #22 邮件投递链耗尽 Tomcat 线程（P1，读码，**未实测**）
- **位置**：`application.yml` 的 `spring.mail` **没有任何 `mail.smtp.timeout` / `connectiontimeout` / `writetimeout`**（JavaMail 默认**无限等待**）；`AsyncConfig.captchaMailExecutor` = core 2 / max 4 / **queue 16** / `CallerRunsPolicy`；`/auth/captcha` 为 `permitAll`，限流键是 `{scene}:{email}`（**换邮箱即绕过**）。
- **链路**：并发第 21 个投递起，**Tomcat 请求线程自己去同步做 SMTP**；服务商被 greylist / 限流 / 链路丢包时这些线程长期不归还 ⇒ 线程池打满、全站不可用；同时向任意第三方地址真实发信。
- **为什么没实测**：本地 Mailpit 是毫秒级本地响应，这条放大链**在本机不存在**（`CaptchaMailSmokeTest` 在 Mailpit 未启动时还会直接跳过）——正是「本地永远遇不到」的典型。
- **修法**：邮件池改 `AbortPolicy`（或加大队列）+ 补齐三个 SMTP 超时 + `/auth/captcha` 加 IP 维度限流（与 #14 合并做）。

#### #23 审计行可被静默丢弃（P1，读码）
- **位置**：`OperationLogAspect.initLog` 把 `uri + "?" + queryString` **整串**写入 `url VARCHAR(255)`；`error_msg VARCHAR(500)` 同理。四个查询 DTO（`UserQuery`/`RoleQuery`/`PermissionQuery`/`LogQuery`）的模糊查询字段**无任何长度约束**。
- **机制**：长 URL → MySQL 1406（`STRICT_TRANS_TABLES` 已实测确认）→ 异步落库抛异常 → 被 `OperationLogServiceImpl.record` 的 catch 吞掉，只留一行 ERROR。
- **后果**：**在 URL 后面挂一长串参数，这个请求就不留审计痕迹**；再叠加 `/api/logs` 前缀被整体排除（#16）与定向删除（#8），审计链可被规避。
- **修法**：落库前 `substring` 截断 + 超长记 WARN（几行）；彻底做法是把列改成 `TEXT`。

#### #24 导入含公式的 Excel（P2，实测）
- 公式**带**缓存值（Excel 另存后的常态）→ EasyExcel 抛 `NumberFormatException: Character a is neither a decimal digit number, decimal point, nor "e" notation exponential mark.` → 经 `UserImportExportServiceImpl` 的 `catch (Exception)` 包成 `1017 + e.getMessage()` **英文原文回显**给调用方。
- 公式**不带**缓存值 → 该单元格**静默读成 `null`**（邮箱列会变成「邮箱不能为空」）。
- 这给 #17 补上了具体触发路径与文案：用户上传一张「用公式算出来」的表格就会踩到。

#### #25 权限缓存失效失败被吞 + 回填覆盖竞态（P1，读码）
- `PermissionCacheServiceImpl.evictUsers` 的 catch 只 `log.warn("…（依赖 TTL 兜底）")`。设计文档「fail-open 不会真的放行」的论证**只在 Redis 整体不可用时成立**：删除命令**单独**失败（单次超时、主从切换）时会话链路完全健康，`@PreAuthorize` 拿到的是**已被回收的旧权限**，直到 30 分钟 TTL 到期。
- 同一处 `load` 是「未命中 → 查库 → `set` 回填」，**无版本号 / CAS**；一旦与 AFTER_COMMIT 的删除交错，仍会把旧权限写回并续 30 分钟。因失效只在撤销时触发，**旧值必然等于「更多权限」，竞态永远落在危险侧**（`docs/design/03` §3 已记该竞态，此处补正概率口径：它与**被影响用户的日常流量**成正比，而非与管理员并发成正比）。

#### #26–#40（要点）
- **#26**：`UserServiceImpl.assignRoles` 既无超管保护，也**没有** `CANNOT_OPERATE_SELF`（禁用/删除/踢人都有 1022）⇒ 管理端「清空自己的角色」一次点击即自锁，且没有接口能捞回来。
- **#27**：`register`/`create`/`createMenu` 都是「查重 → 插入」，未捕获 `DuplicateKeyException` ⇒ 并发/双击拿到 `body 500` 而非 1001/1010/1016。
- **#28**：`GlobalExceptionHandler` 只覆盖 `BusinessException` / `MethodArgumentNotValidException` / `HttpMessageNotReadableException` / `AccessDeniedException`，缺 `BindException`、`MethodArgumentTypeMismatchException`、405、413 ⇒ 全部落到兜底 500，**且不像 400 分支那样补记审计**（`GET /api/users/abc`、`PATCH /api/users/1` 即是）。
- **#29**：`RbacCacheProperties` 是三个配置类里**唯一**没有 `@Validated`/`@AssertTrue` 的（`AuthSessionProperties`、`CaptchaProperties` 都专门防了这个坑）⇒ `qsx.rbac-cache.ttl: 30` 被当成 **30 毫秒**，缓存永不命中、每请求多 2 条 SQL，**零日志零报错**。修复约 5 行。
- **#30**：`TokenAuthenticationFilter` 的 `catch (Exception)` 把**查库异常**也归到「Redis 不可达？」并打上免审计标记 ⇒ Redis 健康时只要 DB 变慢，全员 401 且审计表一条记录都没有，ERROR 文案还把方向指向 Redis。
- **#31**：导出是**先 `selectList` 全表读进内存再判 50000 上限**；导入是**先解析完整个 Excel 再判 1000 行**（ReadListener 里没有早停）⇒ 两个上限都在 OOM 之后才生效；正确做法是 `LIMIT n+1` / 在 `invoke` 里计数即抛。
- **#32**：`pageNum` 无 `@Min/@Max`（`pageSize` 有 `maxLimit=500`，**这条已防护**）⇒ `?pageNum=100000000` 生成 `LIMIT 49999999500,500`；四个查询全用 `LIKE '%x%'`（前导通配符使 `uk_email` 完全用不上），且 `%`/`_` 未转义（`?email=%` 可强制无条件全表扫）。
- **#33**：只限制了 multipart（10MB），JSON 请求体无上限 ⇒ 匿名 `/auth/login`/`/auth/register` 可被巨大 body 打内存。
- **#34**：仓库唯一 DDL 产物是 `sql/init.sql`，而它是 `DROP TABLE` + 重建，且兼作种子数据 ⇒ 生产形态的 schema 演进无路可走（`04` 附 A 的加列方案只能手工执行），误跑一次即全库清空；也没有 profile 隔离让 `debug=true` 在生产形态启动即拒。
- **#35**：未配 `server.shutdown: graceful`，`ThreadPoolTaskExecutor` 用默认 `waitForTasksToCompleteOnShutdown=false` ⇒ 重启/发版时队列里的审计日志与待投验证码邮件**直接丢**；依赖里没有 `spring-boot-starter-actuator`，无探活端点。
- **#36**：`BaseIntegrationTest` 直接跑在开发库上，清理范围含**清空 `sys_operation_log` 全表** ⇒ 建议加「库名不含 test 就拒绝启动测试」的守卫（成本极低，防的是将来某次对着生产配置跑 `mvn test`）。
- **#37**：轮换无宽限窗口（旧 RT 立即 `DEL`）⇒ 多标签页同时刷新、弱网重试、或**轮换成功但响应在网络上丢失**，一律变成强制登出。属严格轮换的固有代价（安全侧），需要产品决策而非单纯修 bug。
- **#38**：`PermissionServiceImpl.page` 只有 `orderByAsc(sort)`，缺 id tiebreaker（同类方法 `getUserMenuTree`/`selectAll` 都补了 id）⇒ `sort` 相同的行跨页顺序不稳定，翻页会重复/漏行。
- **#39**：`MenuCreateRequest`/`MenuUpdateRequest` 的 `type` 是自由字符串、`visible`/`sort` 是任意 `Integer`，而代码按 `type == "MENU"` 判定 ⇒ 写错一个字符，该菜单对所有用户的菜单树静默消失。
- **#40**：缓存 TTL 固定、写入时刻由各请求决定、未命中无单飞 ⇒ 一次角色/权限变更会把 N 个用户的键**同时**删除，随后同一瞬间回填、同一时刻到期，「管理员改一次角色 ⇒ 半小时后一个 DB 尖峰」；单用户键缺失时 N 个并发各查 2 条 SQL。修法：TTL 加 ±10% 抖动 + 单飞锁。
