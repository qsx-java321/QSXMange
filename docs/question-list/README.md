## 阅读前提（2026-09-29 明确）

本项目的定位是**本地开发 / 学习阶段的项目，不以真实投产为目标**，追求的是「按企业级开发的严谨程度把代码写对」。

因此：

- 本目录登记的是**这批代码在严谨尺度下客观存在的缺陷**，而不是「上线阻塞项」——即使永不上线，其中多数（校验缺失、静默失效、口径不一致、审计丢行）也值得当成工程练习修掉。
- 严重度反映**缺陷本身的性质**，不表示修复排期，也不表示「必须修」。已明确不修的项一律进 [02](02-主动放弃与搁置清单.md)，不在清单里留模糊状态。
- 每条新增项都标注**「本地可复现 / 仅真实部署形态暴露」**：前者是指本机跑起来就能验证的（含已实测记录），后者是指本地单人开发永远遇不到、只有多用户并发或真实外部依赖才会暴露的。

## 约定

- **严重度分级（缺陷性质口径，非排期口径）**：
  - **P0** = 会导致系统失控或不可恢复（越权、锁死、唯一真相源被破坏）；
  - **P1** = 会造成功能失效、错误行为、静默不一致，或存在可被利用的缺口；
  - **P2** = 工程规范 / 健壮性 / 容量与性能，不影响当前正确性，但离「企业级严谨」有距离。
- **编号稳定性**：`#1–#18` 编号已冻结（被 `docs/design/05` §7、`docs/test/项目测试报告.md` §六 及本目录内多处引用），**永不重排、永不复用**；新增项从 `#19` 起顺序追加；撤销的项保留编号、只改状态列。
- **每条问题必须给证据**：位置（`文件:行号`）+ 触发条件 + 后果。实测复现的记入 [05](05-实测记录与核验方法.md)，代码推导的注明「未实测」。
- 所有「修复方案」必须经过源码审查后再实施；每项修复需配套机制层测试（断言业务码之外，还要断言库 / Redis 状态）。
- 修复完成后：更新本目录状态列、反向同步 `docs/design/05` §7 与测试报告。
