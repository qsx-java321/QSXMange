## 一、实测复现：#19 邮箱长度 与 #20 大小写口径（同一批 HTTP 实验）

**启动方式**（调试通道取码，避免依赖 Mailpit）：

```bash
java -jar qsx-admin/target/qsx-admin-1.0.0.jar --qsx.captcha.debug=true
# 起服务约 3.6s；--qsx.captcha.debug=true 仅影响取码，不影响本次要验的写入路径
```

**请求模板**：`POST /auth/captcha {scene:REGISTER,email:E}` 取码（debug 模式 `data.code` 直返）→ `POST /auth/register {email:E,password:Abc123456[,nickname:N],captcha:C}`。

| 实验 | 输入 | 原始响应 |
| :--- | :--- | :--- |
| 1 | 邮箱 60 字符（`a×51@test.com`）、**昵称留空** | `{"code":500,"message":"系统繁忙，请稍后重试","data":null}` |
| 2 | 邮箱 132 字符（`b×64@c×63.com`） | `{"code":500,"message":"系统繁忙，请稍后重试","data":null}` |
| 3 | 对照：`probe-ctrl-<ts>@test.com` | `{"code":200,"message":"操作成功","data":null}` |
| 4 | 邮箱 117 字符（`d×64@e×43.test.com`）**带昵称**注册 → 超管 `DELETE /api/users/{id}` | 注册 `200`；删除 `{"code":500,...}`，随后库里该行 `email` 长度 117、**`deleted=0`**（未被删除、邮箱也未被改写） |

**机制解释**：实验 1 撞 `nickname VARCHAR(50)`（昵称留空时默认取邮箱）；实验 2 撞 `email VARCHAR(128)`；实验 4 撞 `UserServiceImpl.delete` 的改写 `email + "#deleted_" + 13 位毫秒`（后缀固定 22 字符 ⇒ 邮箱 ≥ 107 字符必溢出）。三处均为 MySQL `STRICT_TRANS_TABLES` 下的 1406，被 `GlobalExceptionHandler` 兜成 `body 500` + `HTTP 200`。详见 01 #19、03 #19。

> 侧面证据（同一次实验）：实验 4 的 117 字符账号**能成功注册**（带昵称时绕开 VARCHAR(50)），说明「长邮箱账号存在」与「长邮箱账号删不掉」是同一条约束缺失的两面。

### 1.2 #20 漏洞邮箱大小写：同一批实验的第 4 组

| 步骤 | 请求 | 原始响应 |
| :--- | :--- | :--- |
| a | 注册 `CaseProbe-<ts>@test.com`（混合大小写，昵称 `cp`） | `200` |
| b | 用**小写** `caseprobe-<ts>@test.com` 登录 | `200`（`data.email` 回显库中的混合大小写形态 ⇒ 证明库比较 ci、登录不敏感） |
| c | 用**小写**邮箱发 `CHANGE_PASSWORD` 码（带 b 的 token） | `200`，`data.code` 直返 |
| d | 用 c 的码 `POST /auth/change-password` | **`1028`「验证码无效或已过期」** |
| e | 重新登录后改用**原样大小写**邮箱发码 → 改密 | **`200` 成功**（对照） |

⇒ 同一个用户、同一个令牌、同样格式的码，**只差邮箱大小写**：一个失败一个成功。根因见 01 #20、修复见 03 #20。

### 1.3 修复后的反向复验（2026-09-29，A 组落地后原样复跑）

| 场景 | 修复前 | 修复后（复跑） |
| :--- | :--- | :--- |
| 注册 60 字符邮箱 + 昵称留空 | 500 | **200**（昵称按列宽截断为 50） |
| 注册 101 字符邮箱 | 500 | **400**（`@Size` 拦住，message 含"邮箱长度"） |

| 用小写邮箱发 CHANGE_PASSWORD 码 → 改密 | 1028 | **200** |

## 二、实测复现：撤销 #3 所依据的 Excel 单元格类型

**方法**：用项目自己的依赖（EasyExcel 4.0.3 / POI 5.2.5）写一个含 `=HYPERLINK("http://evil","click")` 与 `+cmd|'/C calc'!A1` 的表格，然后 ① 直接看 xlsx 内部 XML；② 用 POI 读回看单元格类型。

**`xl/worksheets/sheet1.xml` 原始输出（关键片段）**：

```xml
<c r="B2" s="2" t="inlineStr"><is><t>=HYPERLINK(&quot;http://evil&quot;,&quot;click&quot;)</is></c>
<c r="D2" s="2" t="inlineStr"><is><t>+cmd|'/C calc'!A1</t></is></c>
```

**POI 读回**：`cell[1] type=STRING value=[=HYPERLINK("http://evil","click")]`、`cell[3] type=STRING value=[+cmd|'/C calc'!A1]`。

**结论**：`t="inlineStr"`、**无 `<f>` 元素** ⇒ 是字符串单元格而非公式，Excel 打开不会执行。原「#3 Excel 公式注入」的机制前提不成立，**结论与修法一并撤销**（`docs/design/05` §7 第 5 条须同步改写）。详见 02 §四.4、03 §五。

**同一实验的副产品（→ #24）**：构造**真正的公式单元格**再让 EasyExcel 读：

| 输入 | 读取结果 |
| :--- | :--- |
| 公式单元格、**无**缓存值 | 该列静默读成 `null`（不报错） |
| 公式单元格、**有**缓存值（`t="str"`） | 抛 `NumberFormatException: Character a is neither a decimal digit number, decimal point, nor "e" notation exponential mark.` |

后者经 `UserImportExportServiceImpl` 的 `catch (Exception)` 变成 `1017 + "Excel 文件解析失败，请检查文件内容：" + e.getMessage()` **英文原文回显**。

## 三、反向核验：登录计时侧信道（结论=**已防护**）

**方法**：对「已注册邮箱 + 错口令」与「不存在的邮箱」各打 10 次 `POST /auth/login`，取中位数/极值；另测两条无 bcrypt 的基线。

| 请求 | 样本 | 结果 |
| :--- | --: | :--- |
| `admin@qsx.com` + 错口令 | 10 | 中位 **0.061s**（0.059~0.065） |
| 随机不存在邮箱 + 任意口令 | 10 | 中位 **0.060s**（0.059~0.061） |
| 基线 `GET /auth/me`（401 路径，无 bcrypt） | 6 | **0.0022s** |
| 基线上传邮箱格式非法（400，无 bcrypt） | 6 | **0.0029s** |
| 本地 BCrypt(10) 单次 `matches` 基准 | — | **52 ms** |

**结论**：两条登录路径耗时**一致（差值 < 2ms，远小于 bcrypt 的 52ms）**，说明「用户不存在」分支也跑了一次等价开销的比对——这是 Spring Security `DaoAuthenticationProvider` 在 `UsernameNotFoundException` 分支里的 dummy bcrypt 补偿。因此 **`docs/question-list/02` 里那句「计时侧信道已实测排除」成立，不要删**。

> 这条同时是个方法论示范：**同一个结论，读码（甚至反编译）可能得出相反答案**（推断「不存在的邮箱不跑 bcrypt，故存在时序差」），而实测把它否掉了。凡涉及"时间/并发/外部依赖"的断言，尽量落到实测。

## 四、机制层证据（SQL 与依赖行为）

| 事项 | 证据 | 用途 |
| :--- | :--- | :--- |
| MySQL 严格模式 | `SELECT @@sql_mode` → `ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` | 超长写入**报错**而非截断（#19 / #23 的前提） |
| 库/列 collation | `SHOW CREATE TABLE sys_user` → `email varchar(128) COLLATE utf8mb4_general_ci`；`SELECT 'a@x.com' = _utf8mb4'A@X.COM' COLLATE utf8mb4_general_ci` → **1** | 邮箱比较**大小写不敏感**（#20 的根因） |
| 审计列宽 | `sys_operation_log.url VARCHAR(255) NOT NULL`、`error_msg VARCHAR(500)`；索引仅 `user_id`/`success`/`create_time` | #23 / #9 / #32 |
| `@Email` 的实际约束 | 依赖级单测（Hibernate Validator 8.0.3）：**本地部分 ≤64**（超了报"格式不正确"）、**每个域名标签 ≤63**，而**总长度没有硬上限**（实测 132 / 196 / 260 字符均通过，324 被拒）。写长邮箱用例时必须靠加长域名，不能加长本地部分 | #19 / 测试用例构造 |
| 依赖版本 | Spring Boot 3.5.16 / MyBatis-Plus 3.5.17 / EasyExcel 4.0.3（POI 5.2.5） / Java 21 | 所有结论的适用范围 |

## 五、已防护清单（反向核验：这些**不要**误报或过度修复）

| 能力 | 核验方式 | 结论 |
| :--- | :--- | :--- |
| `@PreAuthorize` 覆盖 / 越权（IDOR） | 逐个控制器核对：除 `AuthController`（8 个认证端点，5 个 `permitAll`、其余仅需登录且业务层限本人）外，**管理端全部端点一一对应独立权限码**；「查单条」用 `user:get`/`role:get`/`perm:get` 而非复用分页码 | 无缺口 |
| SQL 注入 / 排序注入 / 路径穿越 / 文件名注入 | 全量查询走 `LambdaQueryWrapper` 参数绑定；`@Select` 一律 `#{}`；排序字段全是方法引用常量；导入只用原文件名判扩展名、不落盘、不参与路径；导出文件名是固定名 + 时间戳 | 不成立 |

| 会话脚本原子性 / RT 重放 | 三条 Lua 均原子；`rotate` 先比对 `session.refreshToken` 再删旧键 | 重放窗口已关闭 |
| 令牌形态校验 | `TOKEN_REGEX`（`^[0-9a-f]{64}$`）在**任何 Redis 访问之前**执行 | 无畸形输入面 |

| 键泄漏（无 TTL 的裸键） | 三条会话脚本 + 两条验证码脚本的所有写入都带 `EX`/`EXPIRE` | 不成立 |
| 失效事件被静默丢弃 | 7 个 `publishEvent` 调用点全部在 `@Transactional` 方法内 | 不成立 |
| 缓存失效的反查时机 | 所有受影响用户都在改动关联表**之前**反查；两条反查 SQL 刻意不带 `status`/`deleted` 过滤 | 不成立 |
| `@Async` 自调用失效 | `EmailService`、`AccessLogRecorder` 均为跨 Bean 调用 | 不成立 |
| 登录计时侧信道 | **实测**（见 §三） | 已防护 |


**环境清理（跑完必须做，否则污染开发库）**：

```bash
# 先清关联行、再清用户（顺序不能反：关联表靠 user_id 定位）
```
