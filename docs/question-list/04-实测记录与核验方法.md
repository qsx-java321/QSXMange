## 二、已修复项的实测与反向复验

### 2.1 #19 邮箱长度 与 #20 大小写口径（同一批 HTTP 实验）

**启动方式**（调试通道取码，避免依赖 Mailpit）：

```bash
java -jar qsx-admin/target/qsx-admin-1.0.0.jar --qsx.captcha.debug=true
# 起服务约 3.6s；--qsx.captcha.debug=true 仅影响取码，不影响本次要验的写入路径
```

**请求模板**：`POST /auth/captcha {scene:REGISTER,email:E}` 取码（debug 模式 `data.code` 直返）→
`POST /auth/register {email:E,password:Abc123456[,nickname:N],captcha:C}`。

| 实验 | 输入 | 原始响应（修复前） |
| :--- | :--- | :--- |
| 1 | 邮箱 60 字符（`a×51@test.com`）、**昵称留空** | `{"code":500,"message":"系统繁忙，请稍后重试","data":null}` |
| 2 | 邮箱 132 字符（`b×64@c×63.com`） | `{"code":500,...}` |
| 3 | 对照：`probe-ctrl-<ts>@test.com` | `{"code":200,"message":"操作成功","data":null}` |
| 4 | 117 字符邮箱（带昵称）注册 → 超管 `DELETE /api/users/{id}` | 注册 `200`；删除 `{"code":500,...}`，库中该行 `email` 长度 117、**`deleted=0`** |

**机制解释**：实验 1 撞 `nickname VARCHAR(50)`（昵称留空时默认取邮箱）；实验 2 撞 `email VARCHAR(128)`；
实验 4 撞 `UserServiceImpl.delete` 的改写 `email + "#deleted_" + 13 位毫秒`（后缀固定 22 字符
⇒ 邮箱 ≥ 107 字符必溢出）。三处均为 MySQL `STRICT_TRANS_TABLES` 下的 1406，
被 `GlobalExceptionHandler` 兜成 `body 500` + `HTTP 200`。

#### 2.1.1 #20 大小写口径：同一批实验的第 4 组

| 步骤 | 请求 | 原始响应 |
| :--- | :--- | :--- |
| a | 注册 `CaseProbe-<ts>@test.com`（混合大小写，昵称 `cp`） | `200` |
| b | 用**小写** `caseprobe-<ts>@test.com` 登录 | `200`（`data.email` 回显库中的混合大小写形态 ⇒ 库比较 ci、登录不敏感） |
| c | 用**小写**邮箱发 `CHANGE_PASSWORD` 码（带 b 的 token） | `200`，`data.code` 直返 |
| d | 用 c 的码 `POST /auth/change-password` | **`1028`「验证码无效或已过期」** |
| e | 重新登录后改用**原样大小写**邮箱发码 → 改密 | **`200` 成功**（对照） |

⇒ 同一个用户、同一个令牌、同样格式的码，**只差邮箱大小写**：一个失败一个成功。

## 三、撤销一条 P0 所依据的实测：Excel 单元格类型

**方法**：用项目自己的依赖（EasyExcel 4.0.3 / POI 5.2.5）写一个含
`=HYPERLINK("http://evil","click")` 与 `+cmd|'/C calc'!A1` 的表格，然后
① 直接看 xlsx 内部 XML；② 用 POI 读回看单元格类型。

**`xl/worksheets/sheet1.xml` 原始输出（关键片段）**：

```xml
<c r="B2" s="2" t="inlineStr"><is><t>=HYPERLINK(&quot;http://evil&quot;,&quot;click&quot;)</is></c>
<c r="D2" s="2" t="inlineStr"><is><t>+cmd|'/C calc'!A1</is></c>
```

**POI 读回**：`cell[1] type=STRING value=[=HYPERLINK("http://evil","click")]`、
`cell[3] type=STRING value=[+cmd|'/C calc'!A1]`。

**结论**：`t="inlineStr"`、**无 `<f>` 元素** ⇒ 是字符串单元格而非公式，Excel 打开不会执行。
原「#3 Excel 公式注入」的机制前提不成立，**结论与修法一并撤销**（原修法会给
`-`/`+`/`@` 开头的**正常昵称**加可见撇号，做了比不做更差）。

**同一实验的副产品（→ #24）**：构造**真正的公式单元格**再让 EasyExcel 读：

| 输入 | 读取结果 |
| :--- | :--- |
| 公式单元格、**无**缓存值 | 该列静默读成 `null`（不报错） |
| 公式单元格、**有**缓存值（`t="str"`） | 抛 `NumberFormatException: Character a is neither a decimal digit number, decimal point, nor "e" notation exponential mark.` |

后者经 `UserImportExportServiceImpl` 的 `catch (Exception)` 变成
`1017 + "Excel 文件解析失败，请检查文件内容：" + e.getMessage()` **英文原文回显**。

## 四、反向核验：确认「已防护」的清单（**不要误报或过度修复**）

| 能力 | 核验方式 | 结论 |
| :--- | :--- | :--- |
| `@PreAuthorize` 覆盖 / 越权（IDOR） | 逐个控制器核对：除 `AuthController`（8 个认证端点，5 个 `permitAll`、其余仅需登录且业务层限本人）外，**管理端全部端点一一对应独立权限码**；「查单条」用 `user:get`/`role:get`/`perm:get` 而非复用分页码 | 无缺口 |
| SQL 注入 / 排序注入 / 路径穿越 / 文件名注入 | 全量查询走 `LambdaQueryWrapper` 参数绑定；`@Select` 一律 `#{}`；排序字段全是方法引用常量；导入只用原文件名判扩展名、不落盘、不参与路径；导出文件名是固定名 + 时间戳 | 不成立 |
| 响应体泄漏敏感字段 | `UserVO`/`UserExportRow` 不含 `password`/`deleted`；`CaptchaVO.code` 受 `qsx.captcha.debug=false` 严格门控 | 不成立 |
| `pageSize` 拉全表 | `MybatisPlusConfig` 设 `maxLimit=500`（**注：本项为读码推导，未实测**） | 已防护（`pageNum` 未防护，见 #32） |
| 会话脚本原子性 / RT 重放 | 三条 Lua 均原子；`rotate` 先比对 `session.refreshToken` 再删旧键 | 重放窗口已关闭 |
| 令牌形态校验 | `TOKEN_REGEX`（`^[0-9a-f]{64}$`）在**任何 Redis 访问之前**执行 | 无畸形输入面 |
| 令牌日志泄漏 | 切面与两个 handler 落库字段无令牌/密码；`AuthSession.toString()` 与日志 `mask()` 均脱敏 | 不成立 |
| 键泄漏（无 TTL 的裸键） | 三条会话脚本 + 两条验证码脚本的所有写入都带 `EX`/`EXPIRE` | 不成立 |
| 失效事件被静默丢弃 | 7 个 `publishEvent` 调用点全部在 `@Transactional` 方法内 | 不成立 |
| 缓存失效的反查时机 | 所有受影响用户都在改动关联表**之前**反查；两条反查 SQL 刻意不带 `status`/`deleted` 过滤 | 不成立 |
| `@Async` 自调用失效 | `EmailService`、`AccessLogRecorder` 均为跨 Bean 调用 | 不成立 |
| **登录计时侧信道** | **实测**，见下 | 已防护 |

**计时侧信道的实测方法**：对「已注册邮箱 + 错口令」与「不存在的邮箱」各打 10 次
`POST /auth/login`，取中位数/极值；另测两条无 bcrypt 的基线。

| 请求 | 样本 | 结果 |
| :--- | --: | :--- |
| `admin@qsx.com` + 错口令 | 10 | 中位 **0.061s**（0.059~0.065） |
| 随机不存在邮箱 + 任意口令 | 10 | 中位 **0.060s**（0.059~0.061） |
| 基线 `GET /auth/me`（401 路径，无 bcrypt） | 6 | **0.0022s** |
| 基线上传邮箱格式非法（400，无 bcrypt） | 6 | **0.0029s** |
| 本地 BCrypt(10) 单次 `matches` 基准 | — | **52 ms** |

**结论**：两条登录路径耗时**一致（差值 < 2ms，远小于 bcrypt 的 52ms）**，说明「用户不存在」分支
也跑了一次等价开销的比对——这是 Spring Security `DaoAuthenticationProvider` 在
`UsernameNotFoundException` 分支里的 dummy bcrypt 补偿。因此 `02` 里那句
「计时侧信道已实测排除」**成立，不要删**。

> 这条同时是个方法论示范：**同一个结论，读码（甚至反编译）可能得出相反答案**
> （推断"不存在的邮箱不跑 bcrypt，故存在时序差"），而实测把它否掉了。
> 凡涉及"时间/并发/外部依赖"的断言，尽量落到实测。

## 五、机制层证据（SQL 与依赖行为）

| 事项 | 证据 | 用途 |
| :--- | :--- | :--- |
| MySQL 严格模式 | `SELECT @@sql_mode` → `ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` | 超长写入**报错**而非截断（#19 / #23 的前提） |
| 库/列 collation | `SHOW CREATE TABLE sys_user` → `email varchar(128) COLLATE utf8mb4_general_ci`；`SELECT 'a@x.com' = _utf8mb4'A@X.COM' COLLATE utf8mb4_general_ci` → **1** | 邮箱比较**大小写不敏感**（#20 的根因） |
| 审计列宽 | `sys_operation_log.url VARCHAR(255) NOT NULL`、`error_msg VARCHAR(500)`；索引仅 `user_id`/`success`/`create_time` | #23 / #9 / #32 |
| `@Email` 的实际约束 | 依赖级单测（Hibernate Validator 8.0.3）：**本地部分 ≤64**（超了报"格式不正确"）、**每个域名标签 ≤63**，而**总长度没有硬上限**（实测 132 / 196 / 260 字符均通过，324 被拒） | #19 / 测试用例构造 |
| 依赖版本 | Spring Boot 3.5.16 / MyBatis-Plus 3.5.17 / EasyExcel 4.0.3（POI 5.2.5） / Java 21 | 所有结论的适用范围 |

```bash

#    60 字符可以直接写；超过 74 字符必须靠"加长域名"构造（@Email 限本地部分 ≤64）
E1="$(printf 'a%.0s' $(seq 1 51))@test.com"                       # 60 字符
E2="$(printf 'b%.0s' $(seq 1 64))@$(printf 'c%.0s' $(seq 1 26)).test.com"   # 100 字符
curl -s -X POST localhost:8080/auth/captcha -H 'Content-Type: application/json' \
     -d "{\"scene\":\"REGISTER\",\"email\":\"$E1\"}"              # debug 模式取 data.code

     -d "{\"email\":\"$E1\",\"password\":\"Abc123456\",\"captcha\":\"<code>\"}"

# 2) §四 计时：各打 10 次取中位
for e in admin@qsx.com nobody@test.com; do
  for i in $(seq 1 10); do curl -s -o /dev/null -w "%{time_total} " \
    -X POST localhost:8080/auth/login -H 'Content-Type: application/json' \
    -d "{\"email\":\"$e\",\"password\":\"WrongPass123\"}"; done; echo; done

# 3) §三 Excel 单元格类型：用项目依赖独立跑一个写读程序
```

### 6.2 前置：预置超管现在带强制改密标记

预置超管 `must_change_password=1`，用 `admin123` 登录后只能访问 `/auth/**`，
调 `/api/users` 之类会拿到 **1037**。手工复跑有两种做法：

① 重跑 `sql/init.sql` 后**走一遍真实的改密流程**（这正是 §2.2.2 的做法，跑完再重跑一次 init.sql 复位）；
② 只做接口复现时，执行测试基类同款复位 SQL：

```bash
docker exec mysql mysql -uroot -p123456 -e "UPDATE QSXManager.sys_user
  SET must_change_password = 0 WHERE email = 'admin@qsx.com';"
```

### 6.3 环境清理（**跑完必须做**，否则污染开发库）

```bash
# 先清关联行、再清用户（顺序不能反：关联表靠 user_id 定位）
docker exec mysql mysql -uroot -p123456 -e "
  DELETE ur FROM QSXManager.sys_user_role ur
    JOIN QSXManager.sys_user u ON ur.user_id = u.id
   WHERE u.email LIKE '%test.com';
  DELETE FROM QSXManager.sys_user WHERE email LIKE '%test.com';
  DELETE FROM QSXManager.sys_operation_log WHERE create_time >= '<本次开始时间>';"

# Redis：只删本次相关的键。验证码键按邮箱筛（键名含邮箱），会话键按前缀逐类删
docker exec redis redis-cli --scan --pattern 'qsx:auth:cap:*' | grep 'test.com' | while read -r k; do
  docker exec redis redis-cli DEL "$k" >/dev/null; done
for p in qsx:auth:at: qsx:auth:rt:; do
  docker exec redis redis-cli --scan --pattern "$p*" | while read -r k; do
    docker exec redis redis-cli DEL "$k" >/dev/null; done; done
# 注意：qsx:auth:session:* 与 qsx:auth:perm:* 按键名带 userId，需按本次涉及的用户 id 逐个删
```

> ⚠️ **长邮箱行不会被基类清理覆盖**（其域名里多插了一段标签，`@test.com` 不再相邻 ⇒ 不匹配
> `email LIKE '%@test.com%'`），必须按前缀单独清，例如：
> ```bash
> docker exec mysql mysql -uroot -p123456 -e "USE QSXManager;
>   DELETE FROM sys_user WHERE email LIKE 'aaaa%' OR email LIKE 'caseprobe-%';"
> ```
> （`LIKE` 请用**足够独特的前缀**，别用会命中其它测试用户的宽模式。）

> ⚠️ 不要用 `qsx:auth:*` 通配做"大扫除"：里面同时有本机正在使用的会话键，
> 全清会把在线会话一起删掉（见 `CLAUDE.md` 的清理红线：**按显式前缀清单删，不用通配**）。

**副作用提示**：以 `admin@qsx.com` 登录会**覆盖**既有管理端会话（单端覆盖是设计行为），
跑完需要重新登录。

**一次标准收尾的期望值**：`测试用户=0 / 审计日志=0 / 总用户=1（预置超管） / 测试角色=0 /
可见预置码=29 / ADMIN 绑定=29 / Redis 中 qsx:auth:* 键=0`。

### 7.2 与方案的实际偏差（**改方案前先看这里**）

1. **#2 保护集合 23 → 29**：纳入 6 个预置菜单入口码，新增 6 个 `MENU_ENTRY_*` 常量。
2. **#2 主闸位置**：放在「子节点检查」**之前**——否则对既有子节点又是内置的节点（如 `system`）
   会先返回 1014，让人误以为"删掉子节点就能删它"。有测试锁定该优先级。
3. **#19 上限取值 100**：方案原写 110 是**错的**（110 + 22 = 132 > 128，仍会 500）。
4. **#4 白名单从「三个接口」改为「整个 `/auth/` 前缀」**：过滤器对 `permitAll` 端点同样执行，
   只豁免三个的话，持标志用户连"刷新令牌""发本人验证码改密""忘记密码重置"都被挡住
   ⇒ **AT 一过期就永远拿不到新令牌**。
5. **#4 的 fail-fast 落在配置层**，不是"启动检测默认 hash 失败即拒"（那条会锁死本地环境）。
6. **既有测试的迁移**（实际范围比方案大）：
   - `AdminProtectionTest` 端到端用例改为「操作者从始至终不是超管」的等价构造（原构造依赖
     "先授 ADMIN 再摘掉"，已被 1033 封死）；
   - `RbacTest.assignRoles` helper 由「只断 HTTP 200」改为**返回 body code 并显式断言 200**——
     原写法让「第 2 次分配被 1033 拦下」悄然通过（业务异常也是 HTTP 200），用例**绿着空转**。

### 7.3 教训（都是踩过的）

1. **「移除闸代码重跑确认转红」对"删除/替换"类闸门是破坏性的**。
   第一轮的红跑**真的删掉了** `sys_permission` 的 `role:update` 行（连带 ADMIN 的权限绑定）
   与 ADMIN 角色的 29 条权限绑定。做法修正：这类闸门的回退验证**必须先备份受影响数据**
   （`CREATE TABLE tmp_bak_... AS SELECT ...`），跑完按 `init.sql` 的口径复位并复核；
   第三轮的红跑都是「去掉 set / 去掉判空」类，不改数据，故不需要备份。
2. **回退验证前先确认前置状态确实是"未修复态"**——见 §2.2.4 的警告。
3. **测试邮箱必须落在基类清理模式内**（`email LIKE '%@test.com%'`）：为构造超长邮箱而加长域名后
   `@test.com` 不再相邻 ⇒ **不会被自动清理** ⇒ 跨用例残留，症状是"下次建号莫名 1001"。
4. **IDE 编译器会掩盖编译错误**：它往 `target/classes` 写产物，使 Maven 的增量检查跳过 javac，
   于是语法错误的中间态只在测试期以 `java.lang.Error: Unresolved compilation problems` 暴露。
   同根因的第二个症状：**改了 record / 方法签名后不做 clean**，测试期报 `NoClassDefFoundError`
   指向一个**没改过的**类。遇到这两种症状先 `mvn -o clean test`（已记入 `CLAUDE.md`）。
5. **顺手发现的冗余**：#25 最初写成"解析失败先删坏值再回填"，回退验证时发现**删除是多余的**
   ——回填的 `SET` 已经覆盖坏值，删掉删除动作行为不变 ⇒ 改为只落到回填，少一次往返。

## 八、核验的边界（诚实声明）

- **#22（邮件投递链耗尽线程池）未实测**：本地 Mailpit 是毫秒级响应，该放大链在本机不存在；
  改动依赖真实 SMTP 的故障形态，验证只能靠代码审查 + 真实环境观测。01 已明确标注「未实测」。
- **并发/压测类**（#27 TOCTOU、#25 竞态、#40 雪崩、#31 内存上限）均为读码推导，
  未构造并发或大数据量场景。
- **多实例/集群**（#12、#40 的多实例后果）未实测，本地是单实例 + 单节点 Redis。
- **前端未参与**：本仓库无前端代码；#10（HTTP 200 + 业务码）对前端拦截器的影响、
  #37（多标签并发刷新）的真实表现均未验证。
- **红跑对"删除/替换"类闸门是破坏性的**：见 §7.3 第 1 条。
- **#5 的部署侧未验证**：`application-prod.yml` 指向的仍是本地 Mailpit 语义（#6 主动搁置），
  「接真实邮件服务商」这条路径没有在本机跑过。
