**保护闸优先级**（源码级顺序，有测试锁定，勿调整）：

| 接口 | 顺序 |
| :--- | :--- |
| `PUT /api/users/{id}` | `1004 → 1001 → 1022 → 1020` |
| `PUT /api/users/{id}/roles` | `1004 → 1022 → 1033 → 1034 → 1009` |
| `DELETE /api/users/{id}` | `1004 → 1022 → 1025` |
| `POST /api/users/{id}/kick` | `1004 → 1022 → 1021` |

> **两处刻意的不对称**（勿"顺手统一"）：
> ① 自锁闸 1022 在无操作者上下文（程序内直调 service）时**跳过**——没有"自己"可言；
> ② 闸 2（1034）对同样情形 **fail-closed**（按"不是超管"拒绝）——放行等于给无上下文路径留自助提权口。

## 机制层断言

- **删除用户**：email 改写为 `email + "#deleted_<13 位时间戳>"`（固定 22 字符）后逻辑删除，
  唯一索引随之释放、同邮箱可重注册。
  ⚠️ 这使「邮箱长度上限」与「删除能力」耦合：`UserConstants.EMAIL_MAX = 100`（100 + 22 ≤ 128）
  是**必须维护的不变量**，由 `RegisterRequest` / `UserCreateRequest` / `UserUpdateRequest` / 导入校验四处引用。
- **禁用 / 踢人 / 删除 / 改密** → 会话三键清空、旧 AT 立即 401（`UserKickTest` / `AuthSessionTest` 直查 Redis）。
- **权限缓存**：改角色后提交再失效 `qsx:auth:perm:{userId}`（受影响用户在改动关联表**之前**反查）。
- **并发兜底**：`POST /api/users` 在 INSERT 处捕获 `DuplicateKeyException` 并映射回 **1001**（而非 500）。
