### 1.2 测试策略（双轨制）

| 轨道                      | 手段                                                 | 说明                                                                          |
| :---------------------- | :------------------------------------------------- | :-------------------------------------------------------------------------- |
| **Track A** 自动化集成测试     | `mvn -o test`（MockMvc + **真实** MySQL/Redis，无独立测试库） | 覆盖业务码矩阵、边界、并发与机制层断言；测试数据按 `email LIKE '%@test.com%'` / `test-` 前缀隔离并在用例前后清理 |
| **Track B** 真实 HTTP 逐接口 | 启动 fat jar，逐接口真实调用                                 | 记录「HTTP 方法 + URL + Authorization + 请求体」→「HTTP 状态码 + 完整响应 JSON」，令牌脱敏         |
| **机制层断言**               | 直查 Redis / SQL                                     | 会话三键形态与 TTL、缓存键失效、逻辑删除标记——防止「每请求查库兜底」掩盖漏实现                                  |

> **断言口径**：业务异常一律 **HTTP 200 + body 中的业务码**；参数校验失败也是 HTTP 200 + `code=400`；仅 401/403 使用真实 HTTP 状态码。因此断言一律看 body 的 `code`。

### 3.20 分页边界探针（一次性探针，非断言场景）

用于确认「分页上限是否可被绕过」，均携带超管 Authorization：

| 请求                                   | 观测结果                                                                                                 |
| :----------------------------------- | :--------------------------------------------------------------------------------------------------- |
| `GET /api/roles?pageSize=0`          | HTTP 200 / code=200 / total=1 / pageNum=1 / pageSize=0 / records=0                                   |
| `GET /api/roles?pageNum=0`           | HTTP 200 / code=200 / total=1 / pageNum=1 / pageSize=10 / records=1（归一为 1）                           |
| `GET /api/roles?pageSize=100000`     | HTTP 200 / code=200 / total=1 / pageNum=1 / pageSize=500 / records=1（被 maxLimit 收敛）                  |
| `GET /api/roles?pageSize=-1`         | HTTP 200 / code=200 / total=0 / pageNum=1 / pageSize=500 / records=1（**total 与 records 矛盾**，见 §六 O6） |
| `GET /api/permissions?pageNum=-1`    | HTTP 200 / code=200 / total=29 / pageNum=1 / pageSize=10 / records=10                                |
| `GET /api/logs?pageSize=0`           | HTTP 200 / code=200 / total=6 / pageNum=1 / pageSize=0 / records=0                                   |
| `GET /api/logs?pageNum=0&pageSize=5` | HTTP 200 / code=200 / total=6 / pageNum=1 / pageSize=5 / records=5                                   |

结论：**不存在通过分页参数一次性拉全表的路径**，上限由 `MybatisPlusConfig` 中 `PaginationInnerInterceptor.setMaxLimit(500L)` 兜住。

## 四、会话机制层断言（直查 Redis / SQL）

会话层不经 HTTP，直接读 Redis 校验「机制是否真的生效」——只断言 401 会被每请求查库的 `isEnabled()` 兜底放过。

### 4.1 Redis 三键形态与 TTL

| Key                         | Value                                         | TTL              | 职责                  |
| :-------------------------- | :-------------------------------------------- | :--------------- | :------------------ |
| `qsx:auth:at:{at}`          | userId                                        | **1800s（30 分钟）** | AT 有效性；**删除即吊销**    |
| `qsx:auth:rt:{rt}`          | userId                                        | **604800s（7 天）** | RT → userId；轮换时删旧立新 |
| `qsx:auth:session:{userId}` | Hash{accessToken, refreshToken, firstLoginTs} | **604800s（滑动）**  | 单端覆盖、按用户清理、30 天绝对上限 |

### 4.3 五入口会话清理矩阵

统一入口 `AuthSessionService.remove(userId)`，五个触发点均须清空 AT / RT / session 三键：

## 六、观察项与设计约束（保留现状）

| #  | 项                                                                                          | 说明与判断                                                                                                                                                                                                                           |
| :- | :----------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1  | `GET /auth/login`（方法不允许）触发 `HttpRequestMethodNotSupportedException`，落入兜底返回 500 **且不记操作日志** | 同类还有畸形 JSON、超长上传、404 等；属既有行为，未处理                                                                                                                                                                                                |

### 10.3 本轮观察（无产品缺陷）

- **期望与实测 100% 一致**：39 笔逐条自动比对（含机制层 Redis 断言），无偏差。
- **未注册邮箱连限流计数都不消耗**：`FORGOT_PASSWORD` 场景对未注册邮箱在业务层就提前返回（R6-8），
  既不发信也不写任何 Redis 键——无法据此探测邮箱是否注册；同时意味着该路径不受发送限流约束
  （无副作用，无实际影响，记录备查）。
- **验证码场景之间键空间完全隔离**：同一邮箱在 `REGISTER` 被 60 秒限流后，`FORGOT_PASSWORD` 仍可立即发码（R6-3）。
- **单端登录会一并作废旧 refresh token**：同一账号第二次登录后，第一次登录拿到的 RT 立即失效
  （用它刷新返回 1019）。这是单端覆盖的设计行为，但前端需注意：**同一账号开多个标签页登录会互相踢掉刷新令牌**，
  表现为「另一个标签页静默刷新失败 → 被登出」。
