## 二、已完成任务

### 2.1 P0（已复现 + 已修复）：`status` 无取值约束 → 禁用保护可被绕过

**复现证据**（修复前实测，探针用户用完即清）：

| 操作 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 普通用户 `status=2` | code=200，**会话三键全在**；解冻后旧 AT/RT **复活**（200/200） | **400**，账号未改动、会话保留 |
| 给第二个超管 `status=1` | 1020（保护生效） | 1020（不变） |
| 给第二个超管 `status=2` | **200 —— 超管被禁用** | **400** |
| 给**自己** `status=2` | **200 —— 超管锁死自己** | **400** |

**根因**：系统各处判定「禁用」的谓词不一致 —— `SecurityUser.isEnabled()` 与 refresh 查库兜底用 `status != 0`，而禁用保护与会话清理用 `status == 1`；同时 `UserUpdateRequest.status` 只有 `@NotNull`、`UserCreateRequest.status` 无任何约束，任何非 0/1 取值都能穿透。

**最坏后果**：把唯一超管置 `status=2` 后，该账号请求全 401、登录 1003，**且没有任何接口能改回来**（改回来同样需要超管权限），只能手工改库。

**修法**：① 两个 DTO 加 `@Min(0) @Max(1)`；② `UserServiceImpl` 抽出 `isDisabling(status)`（**非 0 即禁用**）供保护与清理共用，与 `isEnabled()` 统一谓词；③ 补 3 个回归用例。

### 2.2 P1（已修复）：4 项契约 / 一致性缺陷

| # | 问题 | 修法 |
| :--- | :--- | :--- |
| 1 | refresh **第 1 步**（只读反查）Redis 异常直抛 → 500，**第 3 步**（rotate）同类故障 → 1019，同一故障两种客户端契约 | 第 1 步同样捕获并映射 1019（fail-closed），日志留痕 |

| 3 | 改密后会话清理失败被 `catch` 吞掉、仍返回 200 —— 与禁用不同，改密**没有每请求查库的兜底网** | 日志提级为 **ERROR**（可告警可检索）；保持不阻断（密码已落库，返回错误会误导用户） |
| 4 | 会话配置无防呆：`max-lifetime: 30`（人类写「30」，被绑定为 **30 毫秒**）会让所有会话刷新即作废且无任何报错 | 加 `@AssertTrue` 启动期校验（三者 ≥ 1 分钟且 at ≤ rt ≤ max-lifetime） |

## 三、错误与教训

- **技术坑（本会话最核心的发现方式）**：P0 在 112 个用例全绿的情况下存在 —— 因为既有测试只覆盖 `status=0/1` 这条正常路径，而「谓词不一致 + 参数无取值约束」是测试盲区：**断言的都是「合法输入的行为」，没人断言「非法输入必须被拒」**。教训：新增/修改带枚举语义的字段时，除了正向用例必须补「非法取值被拒」的用例；同一业务判定（如「是否禁用」）全系统只能有一个谓词实现。
- **决策失误（自己埋的坑，被审查纠正）**：M2 阶段我给 `RefreshRequest` 加了 `@Pattern`，本意是「挡掉畸形输入、不做无谓 Redis 往返」，结果把形态非法的 refresh 从 1019 改成 400，**破坏了 `README` 自己写明的「refresh 失败一律 1019 → 清登录态」契约**。教训：加校验前先看该失败路径在**对外契约**里承诺了什么；「失败一律 X」这类契约必须全路径贯彻，否则客户端写不出正确的恢复逻辑。
- **决策失误**：把 `update` 的守卫写成 `status == 1` 时，我刻意与既有的保护守卫（也是 `== 1`）保持一致，却没想到系统另一处用 `!= 0` —— 一致性是跟错了对象。教训：判定规则要对齐**语义来源**（`isEnabled()`），不是对齐相邻的那行代码。
- **流程失误**：第一版探针脚本的清理用 `delete ... LIKE 'probe-%@test.com'` 却没指定库名，且把 stderr 重定向到 `/dev/null`，导致**清理静默失败**、探针数据残留在库里（我是从"剩余用户 3 行"才发现的）。教训：清理/回滚脚本必须校验执行结果（打印剩余量并断言），且不要吞掉错误输出。
- **流程失误（他人代劳的排查物）**：审查过程中有临时探针测试文件出现在工作区，我在收尾时**主动核验了工作区与数据库状态**才发现已被清理干净。教训：借用子代理做排查后，收尾必须 `git status` + 数据状态双重核验，不能假设「它会自己清理」。
- **吸取的教训（可复用）**：
  - 参数校验缺失会把「校验」变成「绕过」：`@NotNull` 只保证「有值」，不保证「值合法」。
  - 对外错误码是契约：同一操作因失败发生在不同步骤而返回不同错误码，等于没有契约。
  - 配置项也要防呆：`Duration` 允许纯数字，`30` 与 `30d` 相差 86400 倍且无任何提示。
  - 断言要能证伪：修完 P0 后我用**同一套探针**跑修复前后对照，而不是只看新用例变绿。

## 四、关键技术抉择

- **`status` 限于 0/1，而非在服务层兼容任意取值**：让非法值在入口就被拒，同时服务层用「非 0 即禁用」做纵深防御 —— 即便将来有绕过 DTO 的调用方（如导入路径）也不会出现两套语义。
- **标识（code）改为不可变，而非「改名时提示风险」**：改错一个系统码后，**连改回来所需的接口也一起失配**，提示无法阻止这种不可逆后果；改名需求走「新建 + 重新绑定 + 删旧」。此原则主动扩展到角色编码（理由见 §2.3）。
- **权限缓存回填竞态：维持现状，记录为有界陈旧**（用户拍板）：窗口极窄（毫秒级）、后台系统并发低，且已有 TTL（默认 30 分钟）兜底；若需严格保证，可给缓存键加版本号并在回填时 CAS —— 现在不做，避免为极小概率引入每个请求的额外开销。
- **登出按 userId 吊销：有意保留，不改条件清理**：该竞态（A 端登出时恰好 B 端刚登录）影响的是同一用户的另一个会话；而把登出改成「只清理自己那一对令牌」会引入更糟的失败模式 —— 轮换后令牌变化会让**真正的登出变成空操作**（用户以为已登出、会话仍在），得不偿失。
- **会话脚本仅支持单节点 Redis**：三条 Lua 用前缀拼动态键名且无 hash tag，上集群会 CROSSSLOT。属已知设计约束，写入 README，不做兼容改造。
- **明文令牌作 key**（沿用 09-16 的 D3 决策）：有 Redis 读权限即可直接冒用；本次**订正了此前不准确的表述** —— 收紧不能「收敛在 `AuthSessionServiceImpl` 单类内」，需同时改 `AuthRedisKeys` + 三条 Lua + session 字段。
- **未处理项**：P3 质量项（`mask()` / 前缀 / Lua 清理逻辑重复实现、`TokenProvider` 两个同构方法、测试基类扫删共享 Redis 上全部 `qsx:auth:*` 键、文档两处描述不一致）—— 不影响正确性，留待后续统一清理。
