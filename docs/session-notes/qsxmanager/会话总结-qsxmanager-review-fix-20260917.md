## 二、P0（已复现 + 已修复）：`status` 无取值约束，禁用保护可被绕过

**现象**（修复前实测，探针用完即清）：

| 操作 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 普通用户 `status=2` | code=200，**会话三键全在**，解冻后旧 AT/RT **复活**（200/200） | **400**，账号未改动，会话保留 |
| 给第二个超管 `status=1` | 1020（保护生效） | 1020（不变） |
| 给第二个超管 `status=2` | **200（保护被绕过，超管被禁用）** | **400** |
| 给**自己** `status=2` | **200（超管可锁死自己）** | **400** |

**根因**：系统各处判定「禁用」的谓词不一致 —— `SecurityUser.isEnabled()` 与 refresh 查库兜底用 `status != 0`，而禁用保护与会话清理用 `status == 1`；同时 `UserUpdateRequest.status` 只有 `@NotNull`，`UserCreateRequest.status` 无任何约束，任何非 0/1 的值都能穿透。

**最坏后果**：把唯一超管置 `status=2` 后，该账号请求全 401、登录 1003，**且没有任何接口能改回来**（改回来也需要超管权限），只能手工改库。

**修法**：
1. 两个 DTO 加 `@Min(0) @Max(1)`（`UserCreateRequest` 的 javadoc 本就写着「0-正常，1-禁用」却没约束）；
2. `UserServiceImpl` 抽出 `isDisabling(status)`（**非 0 即禁用**）并让保护与清理共用，与 `SecurityUser.isEnabled()` 同一谓词（DTO 已限 0/1，此处为纵深防御）。

## 三、P1（已修复）：4 项契约/一致性缺陷

| # | 问题 | 修法 |
| :--- | :--- | :--- |
| 1 | refresh **第 1 步**（只读反查）Redis 异常直抛 → 500，**第 3 步**（rotate）同类故障 → 1019；同一故障两种客户端契约 | 第 1 步同样捕获并映射 1019（fail-closed），日志留痕 |
| 2 | `RefreshRequest` 的 `@Pattern` 让形态非法令牌返回 **400**，破坏「refresh 失败一律 1019 → 清登录态」的前端契约 | 去掉 `@Pattern`，形态校验下沉服务层（仍早于任何 Redis 访问），统一 1019；顺带消除了 web 层 DTO 依赖 security 包的分层倒挂 |
| 3 | 改密后会话清理失败被 `catch` 吞掉、仍返回 200 —— 与禁用不同，改密**没有每请求查库的兜底网** | 日志由 warn 提级为 **ERROR**（可告警、可检索）；保持不阻断（密码已落库，返回错误会误导用户） |
| 4 | `AuthSessionProperties` 无取值校验：`max-lifetime: 30`（人类写「30」，实际绑定为 **30 毫秒**）会让所有会话刷新即作废，且启动无任何报错 | 加 `@AssertTrue`：三者均须 ≥ 1 分钟且 `at-ttl ≤ rt-ttl ≤ max-lifetime`，**启动期失败** |

**修复后运行时复跑同一套探针**：4 项全部符合预期，且**合法流程未受影响** —— `status=1` 禁用后旧 AT 401 且会话三键清空；解冻后旧 AT 仍 401、旧 RT 仍 1019（旧令牌不复活）。

## 四、审查发现但**本次未修**的项（待排期）

**P2 · 既有问题（非本次改造引入）**

已修（2026-09-17 第二批，用例 112 → 115）：
- ✅ **停用角色不回收权限**：`selectRoleCodes/selectPermissionCodes` 加 `AND r.status = 0`——角色「停用」现在真正回收其授予的全部权限码（此前只清缓存、回源结果不变，停用形同虚设）。
- ✅ **标识可被改掉导致接口锁死**：权限/菜单标识与角色编码**创建后不可修改**（1023 / 1024）。改为禁止而非提示，是因为改错一个系统码后**连改回来所需的接口也一起失配**；角色编码另有一条更严重的路径——内置超管保护按 `RoleConstants.ADMIN` 匹配编码，改名可让「超管不可踢/不可禁用」静默失配。
- ✅ **`delete()` 的会话清理时机**：由事务内改为提交后（`registerSynchronization` AFTER_COMMIT），回滚不再留下「用户没被删掉、会话却被清空」。
- ✅ **Redis 故障时的 401 写库放大**：认证链路因基础设施异常判为未认证时打标记，401 处理器跳过操作日志落库——否则故障期 100% 请求 401，队列打满后转同步写库，会把 Redis 局部故障升级为数据库+线程池一起被打满。

## 六、教训

- **同一业务谓词散落多处必然错位**：「禁用」在 `isEnabled()` 是 `!=0`、在保护/清理是 `==1`，两者并存时，多出来的取值就是漏洞。判定规则应只有一个实现（本次抽出 `isDisabling`），并由 DTO 层先限死取值范围。
- **参数校验缺失会把「校验」变成「绕过」**：`@NotNull` 只保证「有值」，不保证「值合法」；保护规则写在 service 层时，任何未覆盖的取值都可能绕过它。
- **对外错误码是契约**：同一操作因失败发生在不同步骤而返回不同错误码（500 vs 1019），会让前端无法写出正确的恢复逻辑；形态校验放在参数层返回 400 也算破坏契约——「失败一律 X」这类契约必须全路径贯彻。
- **配置项也要防呆**：`Duration` 允许纯数字，`30` 与 `30d` 相差 86400 倍且无任何提示；关键配置应有启动期校验。
