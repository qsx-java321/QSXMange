## 三、错误与教训

- **做错了什么**：
  - **技术坑 — 冒烟脚本自身有 bug，却被当成被测系统的失败**：`UID` 是 bash 只读变量（赋值静默失败），JSON 取值 helper 里 Python 单引号嵌套导致 `eval` 语法错误 → 首轮 24/31 断言"失败"，全部是脚本问题。**教训：脚本报错时先怀疑脚本，用一条已知正确的调用（如匿名 401）做基线校验，再采信批量结果。**
  - **流程失误 — 清理脚本把 key→userId 映射写反**：按前缀顺序推断归属，误删了 admin 的 RT 键而非孤儿键，留下"AT 在、RT 没了"的半残会话，最后只能整体清掉该会话。**教训：批量删除前先把「要删什么、为什么」打印出来审一遍再执行，不要边算边删。**
  - **断言口径错误**：用 `qsx:auth:*` glob 统计会话键，把 `qsx:auth:perm:*`（权限缓存）也算了进去，断言 3 实得 4。**教训：统计键数量要用精确前缀 `qsx:auth:{at,rt,session}:*`，别用会误伤的宽 glob。**
  - **验证方法失误 — stash 范围过宽导致测试编译不过**：回退验证回归测试时把 `UserMapper` 一并 stash，而测试引用了新增的 `existsRoleCode` → 编译失败。**教训：验证"测试确实转红"时，只 stash 行为改动，保留被测试引用的新增方法（additive 改动）。**
  - **发现文档与代码长期不一致**：设计文档描述的 `EmailService`/`CaptchaService`/`converter`/`domain.enums`/`infrastructure.redis` 包与多张表**从来不存在**，前几轮没人清理，一直在文档里制造"项目未完成"的错觉。
- **吸取的教训**：
  - **判定谓词必须与它要回答的问题同源**（本次与 P2 是同一类缺陷的第二次出现）：`isDisabling` 统一"非 0 即禁用"、`existsRoleCode` 与 `selectRoleCodes` 分离——**复用一条为别的语义设计的查询/谓词去做判定，错位处就是保护缺口**。以后新增任何保护，先自问：我这个判定条件会不会被另一个无关开关影响？
  - **回归测试必须验证「回退后确实转红」**：`AdminProtectionTest` 提交前把生产改动 stash 掉重跑，确认 5 例从绿转红且失败信息为 `expected 1020 but was 200`（即漏洞真的可利用）。恒绿的回归测试比没有测试更危险。
  - **文档也是交付物的一部分**：功能没做就不该在文档里以"待接入/后续规划"形式存在——它会让读者（包括未来的自己）误判项目状态。

## 四、关键技术抉择

- **修复范围取"两道闸"而非只修一处**（向用户确认为分叉后选择）：只修身份判定的话，停用 `ADMIN` 角色仍会让所有人失去 `role:update`，若无人另有权限来源则**系统被锁死、只能改库恢复**。故同时拦截停用（1026）。与既有「超管角色不可删除」对称：一个防删、一个防停。
- **身份判定另开查询，而不是给 `selectRoleCodes` 加开关参数**：授权查询的 `r.status = 0` 语义必须保持纯净；加参数会让"授权/身份"的边界再次模糊，正是本次缺陷的成因。两条查询的分工写进了方法注释。
- **文档处理：删除「未完成功能」，但保留「设计约束与有意取舍」**：单节点 Redis（上集群 CROSSSLOT）、认证链路硬依赖 Redis、权限缓存有界陈旧、登出窄竞态、令牌明文存储——这 5 条**不是待办**，而是已交付系统的固有属性；删掉会让部署者踩 CROSSSLOT、排障时摸不着头脑。故将该节整体重命名并保留，只删除真正的未完成项。
- **提交策略**：沿用仓库既有惯例直接提交 `master`（全历史均如此，且用户工作方式即"里程碑逐步提交"），未另开分支。
