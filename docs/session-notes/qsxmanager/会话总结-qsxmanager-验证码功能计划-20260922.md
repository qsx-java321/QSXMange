## 三、错误与教训

- **技术坑（PowerShell）**：
  - `git rev-parse @{u}` 在 PowerShell 中被解析为 hash literal 报 `Missing '=' operator` → 需用引号 `'@{u}'`
  - PowerShell **不支持 bash heredoc** `$(cat <<'EOF' ...)` → 报「重定向运算符后缺少文件规范」→ 中文提交信息改用单引号消息
  - 教训：本项目开发机是 PowerShell，git 命令里的 `@{}` 和 heredoc 一律绕开或加引号
- **流程失误（方案自审时发现，非代码）**：
  - 初稿「忘记密码」接口遗漏会话销毁步骤（只写了改密销毁）→ 自审补上并同步 D5 表述
  - 初稿未明确「改密验证码通道发送时邮箱必须 = 当前登录用户」→ 已补
- **吸取的教训**：
  - 写计划方案时核对**现状代码实际签名**（注解、业务码、常量）能提前发现边界陷阱（如 `@NotBlank` 与双通道冲突），比纯理论推演可靠
  - 安全设计点（防枚举、跨场景复用、用后即焚）必须在方案阶段写死，避免实现时遗漏

## 四、关键技术抉择

- **D1 Debug 直返管控：先直返、接邮件时再补开关**（用户选择，接受安全债）。理由：本地大学生开发阶段；接邮件时必须补 `qsx.captcha.debug` 开关 + 生产拒绝启动（已登记为高危安全债 R1）
- **D2 后台创建用户不涉验证码**：仅自助流程（注册/忘记密码/改密）用验证码，后台建号走既有 `user:create` 权限
- **D3 重置后不自动登录**：与现有注册/改密语义一致（注册不自动登录、改密后踢下线）
- **D4 验证码策略：6 位 · 5min · 错 5 次作废 · 用后即焚**
- **D5 改密（含忘记密码重置）成功后统一销毁会话（强制下线）**——本轮最有价值的讨论。论证要点：
  - 本项目**单端登录（单会话）**：销毁代价仅「本人重登一次」，无多设备牵连（多端产品"保留当前会话、销毁其他"的中间态在本项目不存在）
  - `refresh` 链路无密码兜底（只看 deleted/status）：不销毁则已流出 RT 最长可续期至 30 天绝对上限
  - 五入口（登出/踢人/禁用/删除/改密）统一收口 `AuthSessionService.remove()` 是项目招牌，不单独开例外
  - 放弃备选：C1 按通道区分销毁（验证码通道销毁/旧密码通道保留）——语义分叉、安全增益≈0；C2 保当前销毁其他——单会话下无意义
- **D6 验证码 key 绑定 `{scene}:{email}` 双维度 + Lua 原子校验**：防跨场景复用 + 消除读改写竞态；Lua 参数字符串化、脚本与使用方同模块
- **发送通道端口抽象 `CaptchaSender`**：Debug 直返实现 → 未来 MQ+邮件实现替换，符合项目端口依赖倒置风格；验证码体系全部落在 `qsx-module-system`，`qsx-security` 内核零改动
