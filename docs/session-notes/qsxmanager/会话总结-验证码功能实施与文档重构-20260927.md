## 三、错误与教训

**技术坑**

- **进程管理用错的匹配模式**：用 `pgrep -f QsxProjectApplication` 判断应用是否停止，而实际命令行是 `java -jar qsx-admin/target/qsx-admin-1.0.0.jar`——模式永不匹配，于是 P0 起的那次实例**一直被误判为已停止**，活到了 P1 验收。后果：新实例启动失败（8080 被占），curl 请求打到旧 jar 上并挂死 8 分钟。
  → **教训**：停服务一律用 PID（`$!` 或 pid 文件）精确停，并**回验端口已释放**；不要用模糊 pgrep。另外 `pkill -f '<自身命令行里也出现的模式>'` 会把执行命令的 shell 一起杀掉（本次遇到两次，退出码 144）。
- **外部服务对不上端点**：`CaptchaMailSmokeTest` 用 `/api/v1/messages/{ID}` 取单封邮件 → 404 且返回纯文本 `File not found` → Jackson 报 `Unrecognized token 'File'`。正确路径是**单数** `/api/v1/message/{ID}`。
  → **教训**：对接外部服务时报「响应不是合法 JSON」，先怀疑**路径/端点**，用 curl 直接看原始响应，而不是盯着解析代码。
- **只跑新用例就以为改完了**：P1 改完后先跑 `CaptchaTest` 全绿，再跑全量时 `BusinessFlowTest.delete_release_email` 转红——同一用例内对同一邮箱注册两次，第二次撞上 60 秒发送间隔，helper 回落到占位码后卡在验证码校验。
  → **教训**：**每个阶段结束必须跑全量**。这次是「跑全量」把问题挡在了提交之前。

**决策失误（被用户纠正）**

- **把设计行为写成了"问题"**：我把「测试撞上 60 秒发送间隔」描述为"踩到的真实问题"。用户纠正：限流按邮箱维度生效**本就是设计如此**（刚被删除账号的邮箱短期内不该再被反复打扰），产品行为没改、改的只是测试侧对真实时序的适配。
  → **教训**：区分「产品缺陷」与「测试对真实时序的适配」，措辞不要混。
- **严重度评估脱离了项目阶段**：我按「可复用基座」的生产标准输出 10 项问题清单，用户明确回应「不影响正常运行，我只是大学生在本地开发阶段写项目」。
  → **教训**：先确认项目阶段与目标再定严重度；已归档事实见 memory `user-background-and-stage`（按「本地会不会真踩到」排序）。
- **端口抽象切错了维度**：我最初拟的是 `CaptchaSender` + `DebugCaptchaSender`。用户提出改为 `EmailService` + Mock/Real 两实现；我指出 Mailpit 本身就是真实 SMTP 服务、按环境切会得到两份逐行相同的拷贝，用户改选「按行为切」。
  → **教训**：端口抽象按**行为差异**切，不要按**环境**切——环境差异往往已经由配置层（`spring.mail.*`）承担了。

**流程与文档**

- **文档里的命令要当契约对待**：拆多模块后，`CLAUDE.md` / `README.md` 记载的 `mvn test -Dtest=X` 必然 `BUILD FAILURE`（`-Dtest` 同时作用于 5 个模块，其余模块无匹配测试类）。本次补 `-Dsurefire.failIfNoSpecifiedTests=false` 修复。
  → **教训**：结构性重构（拆模块、换构建方式）后必须复核文档里的命令是否还能跑。
- **"计划稿仅供参考"要真的逐条核对**：旧计划稿经核对有 9 处硬缺陷，其中依赖位置与条件装配两处会让实施第一步就编译/启动失败，而这些细节在纸面上"看起来无害"。

> 项目硬规则（Lua 参数必须字符串、脚本与使用方同模块、HGET 不用 HGETALL、TTL 下限 1、`@Async` 不自调用、测试清理禁用全表删除等）已在 `CLAUDE.md` 与 `docs/design/02`、`06` 中写明，此处不重复。

## 四、关键技术抉择

| # | 决策 | 理由 / 放弃的备选 |
| :-- | :--- | :--- |
| 1 | 验证码键前缀用 `qsx:auth:cap:*` | 认证域统一命名空间（旧稿用 `qsx:cap:`）。注意测试清理是**显式前缀枚举**而非 `qsx:auth:*` 通配，新键必须登记 |
| 2 | **发送侧限流也走 Lua 原子**（而非 Java 侧 `INCR`+`EXPIRE`） | 拆开写有两个静默故障：中断留下无 TTL 的键把该邮箱永久锁死；每次续期则日限退化成滑动窗口、永不触发。日限键因此改日期串 `{yyyyMMdd}`，TTL 仅在计数为 1 时设 |
| 3 | 注册校验顺序「**唯一性 → 验证码**」 | 校验成功即用后即焚，先校验会把用户手里那张有效的码烧掉（还要再等 60 秒）；同时保住「重复注册 1001」的既有语义 |
| 4 | `EmailService` 两个实现**按行为**切（SMTP / 调试直返），条件装配互斥 | 放弃 Mock/Real 按环境切（Mailpit 就是真实 SMTP，会得到两份相同代码）；将来接只提供 HTTP API 的服务商再加第三个实现 |
| 5 | ~~验证码邮件线程池用**小队列 + CallerRunsPolicy**~~ → **已于 2026-09-29 改为 `AbortPolicy`**（见 `docs/question-list/01` #22） | 原理由：放弃丢弃策略（验证码是用户正在等待的动作，丢码比慢一拍更糟）。<br>**该理由已被推翻**：CallerRuns 会把 SMTP 投递交给**请求线程**同步执行，一旦 SMTP 被 greylist / 限流 / 链路丢包，队列打满就等于 Tomcat 线程被钉死在外部依赖上——丢的这一封用户重发即可，线程池打满没有任何用户能自救 |
| 6 | 1030（两次密码不一致）/ 1031（双通道二选一）在 **Service 层**判 | 放弃 DTO `@AssertTrue`：DTO 校验失败会被统一压成笼统的 400，前端无法把「密码打错」与「参数格式不对」分开提示 |
| 7 | 测试取码**直读 Redis**，Mailpit 只留 1 例 `assumeTrue` 冒烟 | 放弃「通过 Mailpit API 抓邮件取码」：投递是异步的，轮询外部容器慢且脆；直读 Redis 本身就是机制层断言 |
| 8 | 改密密码强度**对齐注册**（字母 + 数字） | 现状改密只校验长度（6-32），比注册还松，等于留了一条「用弱密码覆盖强密码」的路径 |
| 9 | 文档体系：README 只做概览（149 行），设计细节全部进 `docs/design/` 六篇 | 用户明确要求；计划类文档按项目既有约定「交付后归档删除」，历史留在 git 记录 |
| 10 | 「已知缺口」如实写进设计文档而非隐藏 | 10 项缺陷是项目真实属性，写清楚反而让设计文档完整，并可直接作为生产化待办清单 |
